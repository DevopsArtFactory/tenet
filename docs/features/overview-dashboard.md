# Tenet Overview Dashboard

## Purpose

The embedded Tenet dashboard is the current operator-facing entry point for the control-plane prototype.

The UX direction is now a simpler ArgoCD-style drill-down instead of a single dense dashboard. The intended navigation is:
- applications overview first
- application-linked resources second
- concrete resource detail last

The implementation remains fully embedded HTML/CSS/JS with no separate frontend toolchain.

The dashboard routes are source-agnostic on the backend: `tenet-api` can now feed the same `/v1/catalog/*` and `/v1/overview/*` payloads from either a filesystem checkout or a GitHub-backed read-only desired-state catalog without changing the UI route contract.

Operator troubleshooting quick-reference: use `docs/runbooks/operator-troubleshooting.md`
for the compact route/evidence/state/verification matrix across applications
overview, application detail, resource detail, Recent logs, Live inspection,
audit, plan/apply, and queued applies. Its end-to-end resource workflow is the
release-guarded operator path for application detail -> resource detail ->
Related runtime events -> Recent logs / Live inspection -> request-correlation
handoff evidence, so docs and smoke changes should preserve those labels without
requiring live AWS credentials.

## What shipped so far

### 1. Applications overview landing page

The dashboard at `/` now starts from `GET /v1/overview/applications`, a flattened joined read model that already returns one application row per deployment instead of making the client flatten `GET /v1/overview/accounts` just to render the default landing page. The route intentionally preserves the richer joined runtime/rollout/artifact fields already produced by the account overview builder, even though the landing page currently renders only the application-triage subset.

The first page now focuses on:
- application name
- account
- project/app
- sync
- health
- last update

This keeps the first page optimized for triage instead of deep inspection while leaving the joined route useful for search matching and future application-level summary extensions.

### 2. Argo-inspired visual shell

The current UI refresh adds a more opinionated operator-console layout:
- a top hero section with control-plane summary
- summary cards for filter scope, runtime signals, and workspace shortcuts
- account sidebars that separate account metadata from deployment sections
- denser, more readable deployment cards with stronger visual hierarchy
- preserved dark theme and compact pill-based status cues

This is still intentionally lightweight and framework-free.

### 3. Filter toolbar and URL state

The toolbar is client-side and keeps state in the URL for shareable focused views.

Managed query params:
- `q`
- `sync`
- `account`
- `page`
- `accountId`
- `deployment`

Current behavior:
- `account` uses stable `awsAccountId`
- invalid `sync` and `account` values normalize to `all`
- unrelated query params/hash fragments are preserved when updating managed filters
- browser tab titles are derived from the active route and loaded resource/account/deployment identity as safe text, while the static `<title>Tenet Control Plane</title>` remains the non-JS fallback
- search input focus and caret position survive rerenders
- when filters remove all results, the UI renders `Filters hid every application`, summarizes the active filters, and offers a local `Clear filters` action whose assistive label names the active filters; if `/v1/overview/applications` itself returns no rows, the UI instead renders `No visible applications`, directs operators toward catalog loading, runtime status snapshots, or trusted front-door authorization grants, offers an inline `Refresh applications overview` retry after those inputs are fixed, and offers `_self` `Open Operator context details` to jump to `#operator-context-access-details-panel`
- malformed drill-down bookmarks that omit required context, such as `/?page=account` without `accountId` or `/?page=application` without `deployment`, render a polite missing-context empty state and a `_self` `Back to applications` recovery link that preserves existing `q`, `sync`, `health`, and `account` filters

Guarded-read troubleshooting from the embedded dashboard follows the same diagnostic order as the API docs: start with the `Operator context` banner, inspect `identity.authenticated` and `identityProvenance` first for `401` and trusted identity source wiring (`canonical` for `X-Tenet-Authenticated-*`, `alias` for compatibility `X-User-*`, `managed_session_cookie` for Tenet-managed session cookies rendered as `Tenet-managed browser session cookie`, `absent` for missing fields), then inspect read-only `authRuntime.tenetManagedLogin` and `authRuntime.enterpriseSso` if optional GitHub OAuth/session or provider-neutral enterprise SSO groundwork is being configured, then inspect `roles.provenance.source`, `roles.supportedHeaderNames`, `roles.recognizedNames` / `roles.unrecognizedNames`, and `roles.canRead` before allowlist debugging for viewer-role `403`; role provenance intentionally has no `X-User-*` alias path, so `source=absent` means the front door must forward `X-Tenet-Authenticated-Roles`, and non-empty `unrecognizedNames` means forwarded labels are not one of Tenet's capability-granting `viewer` / `operator` / `admin` roles. In repository policy authorization mode, denied-read guidance points at `repositoryPolicy.summary`, matched users/groups, derived roles/deployment grants/project-environment scopes, and the policy source so admins can update `rbac/policy.json`, `rbac/policy.yaml`, or `rbac/policy.yml`; outside that opt-in mode, the trusted front-door role/deployment grant path remains the default. Use `deploymentAccess.summary.matchedCount` / `unmatchedCount` plus bounded `visibleDeploymentExamples` `matchSources` and `unmatchedNames` / `unmatchedNamesTruncated` and project/environment stale-scope evidence (`forwardedProjectCount`, `forwardedEnvironmentCount`, `unmatchedProjects`, and `unmatchedEnvironments`) to explain empty `200 OK` collections and recognize when the UI shows only a bounded stale-name or stale-scope sample, then inspect `accessVerdicts`, their bounded route examples, any collection-read `Collection scope: filtered to visible deployments` cue, any likely-empty `Collection result: likely empty` cue, any deployment-scoped `Scope grants: exact deployments or matching project/environment scopes` cue, and the `Required trusted headers:` fragment to choose the exact guarded route class and front-door header wiring to debug. The shared read `401` copy keeps the trusted front-door retry path when managed login and enterprise SSO are inactive, but can switch to a same-shell provider sign-in handoff when `authRuntime.tenetManagedLogin.active=true` or `authRuntime.enterpriseSso.active=true` reports a same-origin `loginRoute`; plan/apply write-action `401` copy follows the same active-runtime guidance without sending writes until identity is available. Recognized-identity read `403` cards instead offer `Open Operator context details` plus `Retry current page after access update`, preserving the blocked URL while avoiding a misleading sign-in retry for RBAC/deployment-grant failures. The banner surfaces those fields as troubleshooting evidence; it is not a client-side authorization decision and it does not authorize routes client-side.

Desired-state source diagnostics remain compact in the Operator context banner: the compact meta surfaces the current filesystem/GitHub source plus controller-refresh readiness cue from `GET /v1/operator/context`, while expanded details keep the full filesystem no-op explanation, non-secret GitHub repo/ref/path/base URL fields, Redis handoff availability versus unavailable/no-op states, and webhook match/ignored-reason vocabulary. Backend callers can request the same controller-refresh handoff through guarded `POST /v1/controller/refresh`: filesystem sources return `status=filesystem_noop`, while GitHub sources with an available Redis publisher return `202 Accepted` plus `controllerRefresh` evidence. The embedded banner now exposes that manual handoff only when the Operator context diagnostic reports it available, preserves the current bookmarkable URL, disables while in flight, reuses shared operator-write guidance for `401` / `403` responses, and after an accepted processed handoff refreshes the currently active embedded read model once in place. That follow-up read uses the page's existing refresh path, does not rewrite `window.location.search` or `window.location.hash`, does not hide the Operator context success announcement, and does not introduce polling.

On ECS service resource pages, use `Share ECS service event` or `Copy ECS service event link` on the Live inspection event row to hand off one service event. The link preserves the current resource page query state and changes only the hash, so selectors such as `clusterArn` and `resourceInspectionLimit` stay attached to the shared row.

Managed-login and enterprise SSO lifecycle diagnostics remain read-only in the expanded Operator context details: operators can confirm the callback-state/session TTLs, signed-session expiry enforcement, that provider access tokens are neither stored nor returned, that refresh/revocation are unsupported, and that sign-out only clears Tenet's local session cookie. When active `authRuntime.enterpriseSso.logoutRoute` is present, the sign-out handoff uses the provider label (`Google Workspace SSO` / `Okta SSO`) while preserving the current bookmarkable `returnUrl`; configured-but-inactive or unsafe/missing logout routes remain non-clickable.

Release-guard coverage intentionally does not require live GitHub, Google, or Okta credentials: the local/Docker smoke path keeps the default trusted-front-door recovery behavior active when managed login is disabled, while focused router/session tests cover the configured `/auth/logout` cookie-clearing return-URL contract and the Node harness injects an active managed-login diagnostic to verify the `_self` sign-in link preserves the current bookmarkable path/query/hash as `returnUrl`. The same harness also injects active enterprise SSO diagnostics to verify provider-neutral `_self` sign-in links preserve the current bookmarkable path/query/hash as `returnUrl`, including the Google Workspace runtime shape where both `tenetManagedLogin` and `enterpriseSso` are active and the embedded recovery action must still say `Sign in with Google Workspace SSO` instead of presenting it as a GitHub-style managed-login lane, plus the Okta OIDC runtime shape where `provider=okta_oidc` uses the operator-facing `Sign in with Okta SSO` label on application drill-down auth failures. The same injected managed-login diagnostic locks the expanded Operator context sign-out handoff: it links to `/auth/logout?returnUrl=...`, stays in the same shell, and explicitly says it clears only the Tenet-managed session cookie rather than upstream provider or front-door sessions. That release guard covers credential-free managed login for GitHub OAuth, Google Workspace OIDC, and provider-neutral enterprise SSO shell handoffs; provider-token refresh/revocation and long-lived token lifecycle management remain future work rather than embedded-dashboard behavior operators should expect today.

The underlying `/v1/overview/applications` payload is still a richer joined row than the first page renders. It also preserves additive runtime summary, rollout summary, artifact, generation, condition, rollout-context fields (`runtimeSummary.targetType` / `runtimeSummary.strategy` / `runtimeSummary.executionMode`), and the latest human-readable `runtimeSummary.changeDetails[]` copied from controller-authored runtime history when present, so other UI helpers and future slices can reuse the same route without rejoining `/v1/overview/accounts`. Application rows may also include an additive `troubleshootingRecommendation` object when existing joined evidence already points at a conservative next check; quiet synced applications omit it. Recommendations are read-only hints derived from managed drift, unhealthy/error status, unavailable runtime observations, or retained runtime events, with `reason`, `summary`, optional `resourceType` / `resourceName`, and existing Tenet read-route `handoffs`. When more than one signal exists, Tenet keeps the triage order conservative: managed drift, then unhealthy/error status, then unavailable live-observation evidence, then retained runtime-event context. They do not trigger live AWS/log reads while building the overview. Client-side search now also matches additive `runtimeSummary.deployedArtifact`, concise `runtimeSummary.conditions[]` summaries, and `runtimeSummary.changeDetails[]` when those fields are present, but it intentionally skips placeholder `—` text so missing runtime context does not create noisy matches.

### Applies monitor

`TENET_AWS_ENABLE_APPLY=true` queues local-safe apply handoff metadata only; it requires no live AWS credentials and does not perform live AWS mutation. The backend active apply collection is `GET /v1/applies?status=active`: it returns queued plus running local-safe apply handoff records newest-first, including claim freshness fields (`claim.lastHeartbeatAt` / `claim.expiresAt`) when present, and performs no executor mutation. `GET /v1/applies?status=running` returns only claimed/in-flight running records for dashboards that do not want queued handoffs. `GET /v1/applies?status=active&claim=stale` narrows the active collection to running records whose claim lease is stale or expired, while `GET /v1/applies?status=queued` remains the exact queued subset. The bookmarkable `/?page=applies` monitor defaults to queued work, preserves manual `Refresh applies`, and exposes explicit queued/active/stale view controls; `/?page=applies&appliesView=active` shows the active collection and `/?page=applies&appliesView=stale` shows stale active claims so operators can inspect claimed/running handoffs without leaving the embedded shell. The monitor renders loading, empty, unavailable, generic fetch-error, and shared operator-read `401` / `403` guidance states without changing apply executor behavior. Loading/unavailable/generic-error monitor states keep the same JSON handoff, `Copy read route`, refresh, and Applications overview recovery actions as empty views so operators can retry or inspect the backing read route instead of landing on a dead end. Populated monitor views now add summary metrics labeled `Queued applies`, `Lifecycle signals`, `Operation signals`, and `Claim signals` above the rows so operators can spot pending claims or stale/attention-needed handoffs before scanning individual records. Populated rows show deployment name, apply id, queued/running status, created time, operation progress, worker ID when claimed, heartbeat/lease freshness copy, and execution-readiness label/summary/evidence when backend `executionReadiness` is present; records without backend preflight data show explicit missing-preflight fallback copy so reviewers do not mistake local-safe handoff metadata for live AWS readiness. Rows keep `_self` `Open plan/apply workspace` links back to `/?page=plan&deployment={deploymentName}&applyId={applyId}` for deeper review.

Local-safe apply executor release guard: reviewers should verify the active collection (`GET /v1/applies?status=active`), stale active-claim collection (`GET /v1/applies?status=active&claim=stale`), queued exact subset (`GET /v1/applies?status=queued`), running exact subset (`GET /v1/applies?status=running`), terminal exact subsets (`GET /v1/applies?status=failed`, `GET /v1/applies?status=succeeded`, and `GET /v1/applies?status=cancelled`), stored apply read (`GET /v1/applies/{applyId}`), non-mutating preflight read (`GET /v1/applies/{applyId}/preflight`), read-only execution preview (`GET /v1/applies/{applyId}/execution-preview`), claim (`POST /v1/applies/{applyId}/claim`), heartbeat (`POST /v1/applies/{applyId}/heartbeat`), and transition (`POST /v1/applies/{applyId}/transitions`) routes together. This local-safe record lifecycle does not perform live AWS mutation. The read-only `/?page=applies` monitor defaults to the queued subset read, keeps explicit queued/active/stale view controls (`?appliesView=active` and `?appliesView=stale`), keeps `Refresh applies` as the explicit reread action, translates claim heartbeat/lease metadata into fresh/stale/pending operator copy, lets operators load a row-local non-mutating execution preview (`GET /v1/applies/{applyId}/execution-preview`) without changing the selected `appliesView`, links operators back to the plan/apply workspace for full review (the plan/apply workspace for detail review remains the primary handoff), and keeps JSON handoff, `Copy read route`, refresh, and Applications overview recovery actions visible on populated, empty, loading, unavailable, and generic fetch-error monitor states. Empty monitor states are actionable: queued empty points operators back to plan/apply workspaces, active empty explains that work may be terminal or still unclaimed, and stale empty is called out as the healthy recovery-queue state.
