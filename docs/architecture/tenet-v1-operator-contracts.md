# Tenet v1 operator contracts

This document preserves the detailed operator-facing endpoint, read-model, auth, resource, and smoke-verification contracts that used to live in the root README. The root README is intentionally slim; keep detailed string-contract coverage here or in the narrower feature and architecture docs.

Tenet is a repository-driven deployment control plane for multi-account environments.

The project is aimed at giving operators one place to understand what should be running, what is actually happening now, and how a deployment is progressing across EC2 and ECS targets. The current product direction is an ArgoCD-inspired workflow: start from a simple applications overview, drill into an application, then drill further into the concrete resource that matters during rollout or troubleshooting.

Today, Tenet is still early-stage and intentionally conservative. The focus is on a strong control-plane core, clear runtime read models, shipped immutable plan/apply record writes, and an operator-friendly embedded UI before live AWS execution and mutation workflows are added.

## What Tenet does

At a high level, Tenet:
- reads deployment intent from either a local repository checkout or a GitHub-backed read-only manifest tree
- compiles that intent into a validated internal catalog
- joins desired state with runtime status snapshots
- exposes that combined view through a small control-plane API and embedded UI
- helps operators inspect rollout state, runtime history, linked resources, and recent operational context

The current UI flow is:
- Applications overview
- Application detail
- Resource detail

The overview intentionally stays compact: rows show the app name, account/environment, sync, health, and one dominant `Open application` action; runtime-events and workspace shortcuts stay behind `More actions`, and expanded operator/auth diagnostics stay behind `Show access details`.

This keeps the first page simple and pushes deeper operational detail into drill-down pages where it is easier to understand. The applications toolbar also includes an `Applications JSON` handoff to `GET /v1/overview/applications`, so operators can inspect the exact joined payload driving the first page when filters, auth, or catalog/status inputs look surprising. The summary distinguishes the latest deployment runtime update from the embedded page's own `Applications read refreshed` timestamp, making it clear when the UI last re-read the joined applications model. When the applications list is empty, the UI now distinguishes between filters hiding known rows and `GET /v1/overview/applications` returning no visible applications at all, so operators know whether to clear filters or check catalog/status/auth inputs; the no-applications state keeps an inline `Refresh applications overview` retry next to its recovery guidance and links directly to `#operator-context-access-details-panel` for trusted front-door diagnostics. The embedded application/resource/drift/plan/audit pages now also keep explicit breadcrumb chrome in the same shell so prior drill-down levels stay bookmarkable `_self` links, the current destination stays visible as a non-click chip, and the account step appears when Tenet already knows the deployment's `awsAccountId`. The application page quick-nav now makes the overview-to-detail hierarchy explicit with an `_self` `Applications overview` return link plus a non-click `Application detail` chip, while the bookmarkable account page now mirrors that same orientation pattern with an `_self` `Applications overview` return path plus a non-click `Account detail` chip. The deployment workspaces now use that same hierarchy pattern too: their shared quick-nav exposes `_self` `Applications overview` and `Back to application` return paths, keeps the active drift/plan/audit destination as a non-click chip, and still preserves compact bookmarkable `On this page` fragment links plus the existing lateral `_self` jumps to sibling workspaces or resources without backing out first. Browser tab titles follow the active route as safe text, so multiple open Tenet tabs identify the current application, account, resource, drift view, plan/apply workspace, or audit feed without changing the bookmarkable URL.

On application detail, `resourceFilter` is UI query state only; it is not sent to `GET /v1/overview/applications/{deploymentName}` and does not add a read-route variant. The filter matches linked-resource type, name, and description text after the application-detail payload is loaded. The filtered-empty state is distinct from the no-resource state so operators can tell whether client-side filtering hid resources or the read model reported none. Application-detail links and filter controls must preserve `q`, `sync`, `account`, `deployment`, and hash state while changing only `resourceFilter`.

## Architecture

Tenet is currently built from four main layers.

### 1. Repository-backed desired state
Tenet expects a repo-like manifest structure with accounts, environments, and deployments. Both `tenet-api` and `tenet-controller` can read that desired state from either:
- a local checkout selected with `TENET_CATALOG_SOURCE=filesystem` plus `TENET_REPO_ROOT`
- a GitHub-backed read-only source selected with `TENET_CATALOG_SOURCE=github` plus `TENET_CATALOG_GITHUB_*`

The same JSON/YAML manifest codec and catalog compiler sit behind both modes, so `/v1/catalog/*` and `/v1/overview/*` keep the same response contract regardless of where desired state was loaded from. `TENET_REPO_ROOT` remains the filesystem-mode input when you want a local checkout; it is not a universal runtime requirement.

### 2. Catalog compilation
The manifest tree is loaded and validated into a compiled catalog. This gives Tenet a stable internal model for:
- account placement
- environment targeting
- deployment strategy
- desired artifacts
- rollout intent

### 3. Runtime status layer
Tenet keeps runtime status separately from desired configuration. Runtime snapshots can be stored in the filesystem or Redis and are used to represent things like:
- sync state
- health state
- rollout progress
- conditions
- bounded runtime history

### 4. Read models and operator UI
Tenet joins desired state and runtime state into read models that power:
- the embedded browser UI
- drill-down pages for applications and resources
- operational views such as rollout context, immutable plan previews, immutable apply requests, deployment events, and recent logs

The embedded UI is intentionally lightweight: static HTML/CSS/JS served directly by the Go API. That keeps the product easy to run locally while the control-plane model is still evolving.

## How to use Tenet

### Run locally against the example repository

```bash
TENET_CATALOG_SOURCE=filesystem \
TENET_REPO_ROOT=$(pwd)/examples/local-repo \
TENET_STATUS_PATH=$(pwd)/examples/local-status/deployments.json \
TENET_API_ADDR=:18083 \
go run ./cmd/tenet-api
```

For manual `go run ./cmd/tenet-api` flows, `tenet-api` listens on `TENET_API_ADDR`, not `TENET_API_PORT`. Use `TENET_API_ADDR=:18083` as a safe local example before opening the UI.

Then open:

```bash
http://localhost:18083/
```

You should land on the applications overview page.

### Run `tenet-api` against a GitHub-backed desired-state catalog

```bash
TENET_CATALOG_SOURCE=github \
TENET_CATALOG_GITHUB_REPOSITORY=acme/platform-config \
TENET_CATALOG_GITHUB_REF=main \
TENET_CATALOG_GITHUB_PATH=tenet \
TENET_CATALOG_GITHUB_TOKEN=*** \
TENET_STATUS_PATH=$(pwd)/examples/local-status/deployments.json \
TENET_API_ADDR=:18083 \
go run ./cmd/tenet-api
```

Optional GitHub source settings:
- `TENET_CATALOG_GITHUB_BASE_URL` for GitHub Enterprise Server or tests
- `TENET_CATALOG_GITHUB_REF` to pin a branch, tag, or commit
- `TENET_CATALOG_GITHUB_PATH` to point Tenet at a repo-relative manifest root such as `tenet` or `catalog/tenet`
- `TENET_CATALOG_GITHUB_TOKEN` when the repo is private or rate limits require auth

Startup validation is explicit:
- Tenet rejects ambiguous config when `TENET_REPO_ROOT` and `TENET_CATALOG_GITHUB_*` are both set without `TENET_CATALOG_SOURCE`
- `TENET_CATALOG_SOURCE=filesystem` requires `TENET_REPO_ROOT`
- `TENET_CATALOG_SOURCE=github` requires `TENET_CATALOG_GITHUB_REPOSITORY`
- `TENET_AWS_ENABLE_APPLY=true` still requires `TENET_REPO_ROOT` because the local-safe executor only supports the filesystem source

The read-model contract stays the same in both modes. For example:

```bash
curl http://localhost:18083/v1/catalog/summary
```

```json
{"accountCount":1,"environmentCount":1,"deploymentCount":2}
```

Every HTTP response from `tenet-api` also carries a `Request-Id` header. If your client already sends `request-id`, Tenet echoes it back; otherwise it generates one. Capture that value when an API call fails and use the same ID to correlate request-scoped logs and any handler/provider work that reads `api.RequestIDFromContext(ctx)`.

`tenet-api` now emits one structured JSON log line per API/UI request with stable fields including `request_id`, `method`, `path`, `status`, `duration_ms`, and `result`. Panic recovery logs a separate correlated panic event, keeps the process alive, and returns a generic `500` response that includes the same request ID without leaking a stack trace to the client.

When a request times out, Tenet returns an explicit correlated `503` response and emits the matching request log with `result=timeout`. The same request context now flows through the catalog, overview, and status read providers, so GitHub-backed desired-state loads and status-store joins can stop work promptly when the client disconnects or the request deadline expires.

### Trusted front-door auth


Front-door auth remains additive and opt-in. Tenet still supports the existing trusted-header mode for installations that authenticate operators before requests reach the API. The provider-neutral enterprise SSO boundary is documented in `docs/architecture/tenet-v1-enterprise-sso.md`; that boundary keeps GitHub OAuth, Google Workspace OIDC, and Okta OIDC as active managed-login providers only when explicitly configured, keeps Okta SAML diagnostic-only, keeps Google Workspace/Gmail identity-only, uses local fake IdP tests instead of live credentials, and treats repository-backed RBAC policy diagnostics as the shipped first policy foundation for mapping users/groups to Tenet roles and scopes. Provider-token refresh/revocation, upstream provider/front-door logout, and Okta SAML runtime activation remain future work. Repository-backed policy route authorization is shipped as an explicit filesystem-catalog opt-in via `TENET_API_AUTHORIZE_WITH_REPOSITORY_RBAC_POLICY=true`; it is not enabled by provider activation alone. Use concrete non-secret provider mode examples in operator docs: `TENET_AUTH_PROVIDER=github`, `TENET_AUTH_PROVIDER=google_oidc`, `TENET_AUTH_PROVIDER=okta_oidc`, or `TENET_AUTH_PROVIDER=okta_saml`; keep credential-bearing values redacted or placeheld separately. The API can now also run explicitly configured Tenet-managed GitHub OAuth, Google Workspace OIDC, or Okta OIDC browser login: `GET /auth/login/github`, `GET /auth/login/google`, or `GET /auth/login/okta` creates one-time callback state, redirects to the configured provider, the matching callback route exchanges the code, persists the normalized identity, and issues a signed `tenet_session` cookie (`HttpOnly`, `SameSite=Lax`) that later requests can project into the authenticated request actor. When that runtime is active, `GET /auth/logout` and `POST /auth/logout` clear only the Tenet-managed `tenet_session` cookie with the same cookie attributes and redirect to a validated in-app `returnUrl` (default `/`). Clearing this cookie does not sign the operator out of GitHub, does not clear an upstream front-door session, and does not change trusted front-door header precedence. The callback marks that cookie `Secure` whenever the request is already HTTPS, when a trusted front door forwards `X-Forwarded-Proto: https` / `Forwarded: proto=https`, or when operators explicitly enable the `TENET_AUTH_SESSION_COOKIE_SECURE` override; local HTTP development keeps the cookie non-`Secure` so `make smoke-local`-style workflows remain usable. `GET /v1/operator/context.authRuntime.tenetManagedLogin` reports the same non-secret cookie-security evidence through `sessionCookieSecureOverride`, `sessionCookieSecureForRequest`, and `sessionCookieSecureSources` so operators can confirm whether the current diagnostic request arrived through a secure-cookie path without inspecting `Set-Cookie` manually. The internal `authprovider` package provides GitHub OAuth, Google Workspace OIDC, and Okta OIDC authorization-code primitives for managed-login integration work, the internal `authidentity` package provides a small JSON-backed identity-store contract for normalized provider identities, and the internal `authstate` package provides a JSON-backed OAuth callback state store with expiry and one-time consume semantics for future CSRF/state validation. When the runtime variables are complete for GitHub (`TENET_AUTH_PROVIDER=github`, `TENET_GITHUB_OAUTH_CLIENT_ID`, `TENET_GITHUB_OAUTH_CLIENT_SECRET`, `TENET_GITHUB_OAUTH_REDIRECT_URL`, shared state/identity stores, and `TENET_AUTH_SESSION_SECRET`), `tenet-api` wires the GitHub provider plus JSON-backed state/identity stores and reports `authRuntime.tenetManagedLogin.active=true` from `GET /v1/operator/context`. When the runtime variables are complete for Google (`TENET_AUTH_PROVIDER=google_oidc`, the `TENET_GOOGLE_OIDC_*` client/issuer/redirect settings, shared state/identity stores, and `TENET_AUTH_SESSION_SECRET`), `tenet-api` wires the Google provider plus the same JSON-backed state/identity stores and reports the active enterprise SSO diagnostic without storing or returning provider access tokens. The runtime stays disabled when any setting is absent, keeps non-secret `requiredSettings` / `missingSettings` diagnostics, and never logs or returns configured secrets. The shipped managed-login runtime supports GitHub OAuth, Google Workspace OIDC, and Okta OIDC browser login today; Okta SAML provider selection remains represented as inactive non-secret diagnostics under `authRuntime.enterpriseSso`, while provider-token refresh/revocation, upstream provider/front-door logout, and long-lived token lifecycle management remain future work. The legacy `/api/v1/auth/*` route family remains unregistered. The same diagnostic returns non-secret `requiredSettings` and `missingSettings` arrays so operators can tell whether managed login is disabled because configuration is absent, partial, or names an unsupported provider without exposing secret values.


`GET /v1/operator/context.authRuntime.enterpriseSso` is the provider-neutral diagnostic surface for the first enterprise SSO runtime slice. For `TENET_AUTH_PROVIDER=google_oidc` (or the legacy `google` alias), the managed-login runtime is active when the Google client, redirect, issuer, state-store, identity-store, and session-secret settings are complete. The diagnostic canonicalizes the Google Workspace runtime provider to `google` even when operators configure the preferred `google_oidc` mode, matching the OAuth provider implementation and smoke assertions. For `TENET_AUTH_PROVIDER=okta_oidc`, the same managed-login runtime is active when the Okta issuer, client, redirect, state-store, identity-store, and session-secret settings are complete. For `TENET_AUTH_PROVIDER=okta_saml`, Okta SAML remains diagnostic-only and inactive; complete Okta SAML preflight now also validates that metadata/ACS values are absolute HTTP(S) URLs and that `TENET_OKTA_SAML_ACS_URL` points at `/auth/callback/okta/saml` before reporting `configured=true`. The diagnostic reports the canonical provider, sign-in/callback/logout routes, `requiredSettings`, `missingSettings`, `invalidSettings`, shared state/identity/session-secret booleans, and `active` state without returning secrets, raw tokens, SAML assertions, authorization codes, or private keys. Google Workspace/Gmail means identity login only; it does not grant Tenet Gmail mailbox access. Example configured Google diagnostic:

```json
{
  "authRuntime": {
    "enterpriseSso": {
      "configured": true,
      "active": true,
      "provider": "google",
      "requiredSettings": ["TENET_AUTH_PROVIDER", "TENET_GOOGLE_OIDC_CLIENT_ID", "TENET_GOOGLE_OIDC_CLIENT_SECRET", "TENET_GOOGLE_OIDC_ISSUER_URL", "TENET_GOOGLE_OIDC_REDIRECT_URL", "TENET_AUTH_STATE_STORE_PATH", "TENET_AUTH_IDENTITY_STORE_PATH", "TENET_AUTH_SESSION_SECRET"],
      "missingSettings": [],
      "loginRoute": "/auth/login/google",
      "callbackRoute": "/auth/callback/google",
      "logoutRoute": "/auth/logout",
      "stateStoreConfigured": true,
      "identityStoreConfigured": true,
      "sessionSecretConfigured": true
    }
  }
}
```

`make smoke-local` and `make smoke-docker` restart the API with fake local Google OIDC, Okta OIDC, and Okta SAML settings to prove Google and Okta OIDC report active managed-login/enterprise-SSO runtimes while Okta SAML remains configured-but-inactive, non-secret, credential-free, and explicit about route placeholders plus required/missing/invalid settings. Use these settings only when every request reaches Tenet through a front door that authenticates the caller and strips any client-supplied `X-Tenet-Authenticated-*`, `X-Tenet-Authenticated-Roles`, `X-Tenet-Authorized-Deployments`, `X-Tenet-Authorized-Projects`, `X-Tenet-Authorized-Environments`, and trusted-alias `X-User-*` headers before forwarding trusted values. Do not expose a header-trusting `tenet-api` instance directly to untrusted clients.

Tenet currently has two intentionally separate identity header families:

| Header family | Trusted source | Current use |
| --- | --- | --- |
| `X-Tenet-Authenticated-*`, `X-Tenet-Authenticated-Roles`, `X-Tenet-Authorized-Deployments`, `X-Tenet-Authorized-Projects`, `X-Tenet-Authorized-Environments` | Authenticating front door only | Request-scoped route authorization, `GET /v1/operator/context` diagnostics, and optional projection into persisted plan/apply/audit actor fields when no explicit actor headers are present. |
| `X-Tenet-Actor-*` plus compatible `X-User-*` aliases | Local proxy, smoke, or trusted integration creating immutable records | Persisted actor metadata on plan previews, apply requests, and audit projections; this family does not authorize routes by itself. |

Keep that split intact when integrating an external front door: the provider should authenticate the user, strip spoofable inbound trust headers including `X-User-*` aliases, and then forward only the trusted authorization headers Tenet is configured to consume. Tenet-managed GitHub, Google Workspace OIDC, and Okta OIDC sessions are signed cookies minted only by their configured callback routes; `/auth/logout` only expires that Tenet-managed cookie and redirects back to a safe in-app URL. Tenet does not treat raw browser-supplied `X-User-*` headers as a login session, and clearing the Tenet cookie does not remove trusted front-door identity headers from a request.

The auth/RBAC toggles below are boolean examples. Set them to `true` only on API instances that are reachable exclusively through that trusted front door.

- `TENET_API_TRUST_AUTHENTICATED_HEADERS=true` trusts front-door-forwarded `X-Tenet-Authenticated-Id`, `X-Tenet-Authenticated-Name`, and `X-Tenet-Authenticated-Email`. When those explicit trusted fields are absent, the same trusted authenticated-identity path also accepts additive `X-User-ID`, `X-User-Name`, and/or `X-User-Email` aliases. `X-Tenet-Authenticated-*` values still win over `X-User-*` aliases for that trusted authenticated identity path.
- `TENET_API_ENFORCE_AUTHENTICATED_IDENTITY=true` requires authenticated identity on `POST /v1/plans/deployments/{deploymentName}`, `POST /v1/applies/plans/{planId}`, `POST /v1/applies/{applyId}/claim`, and `POST /v1/applies/{applyId}/transitions`. Unauthenticated requests fail with `401 Unauthorized` plus `unauthenticated: authenticated identity is required for this operator write route`. When explicit actor headers are absent, the trusted authenticated identity path projects that identity into persisted plan/apply/audit actor fields.
- In the embedded plan/apply workspace, the same operator guidance stays explicit: authenticated identity is required on operator write routes. When Tenet-managed login is inactive, unauthenticated writes tell operators to retry the same bookmarkable plan/apply action through the trusted front door instead of sending those writes directly to Tenet; active enterprise SSO can only replace that recovery path when the enterprise diagnostic also reports an active same-origin `loginRoute`. When the optional managed-login or enterprise SSO diagnostic reports an active same-origin login route, guarded read recovery can offer the configured Tenet-managed GitHub or provider-neutral enterprise SSO sign-in handoff while preserving the current `returnUrl`. For the GitHub managed-login runtime specifically, guarded read recovery can offer the configured Tenet-managed GitHub sign-in handoff while preserving the current `returnUrl`. If a write reaches Tenet but returns deployment-access `403`, the failure card tells operators to request either an exact `X-Tenet-Authorized-Deployments` grant for that deployment or matching `X-Tenet-Authorized-Projects` plus `X-Tenet-Authorized-Environments` scopes that prove the catalog placement for the deployment being written.
- `TENET_API_ENFORCE_OPERATOR_ROLE_AUTHORIZATION=true` trusts `X-Tenet-Authenticated-Roles`, normalizes comma-separated roles, and requires one operator-capable `operator` / `admin` role on operator write routes. Role forwarding intentionally has no `X-User-*` compatibility alias; `roles.provenance.source=absent` means the front door must forward `X-Tenet-Authenticated-Roles` before role-gated reads or writes can pass. Authenticated callers without one of those roles get `403 Forbidden` plus `forbidden: authenticated operator role is required for this operator write route` before any plan/apply lookup.
- `TENET_API_ENFORCE_DEPLOYMENT_READ_AUTHORIZATION=true` trusts `X-Tenet-Authorized-Deployments` as a comma-separated exact deployment allowlist for existing exact grants. It also accepts additive `X-Tenet-Authorized-Projects` plus `X-Tenet-Authorized-Environments` scopes for guarded deployment reads and immutable writes; Tenet only widens access when it can prove the deployment's catalog placement matches both a forwarded project and environment. Exact deployment grants continue to win for deployment-specific access. Guarded collection reads (`GET /v1/overview/applications`, raw catalog collections such as `GET /v1/catalog/deployments`, `GET /v1/status/deployments`, `GET /v1/overview/accounts`, and unscoped `GET /v1/audit-logs`) filter to the union of exact deployment grants and project/environment catalog matches. Missing, stale, or non-matching grants return `200 OK` with `[]` or `{"entries":[]}` on collection routes, while scoped reads return the existing operator-read `403` unless exact deployment membership or project/environment placement proves access.
- When both `TENET_API_ENFORCE_OPERATOR_ROLE_AUTHORIZATION=true` and `TENET_API_ENFORCE_DEPLOYMENT_READ_AUTHORIZATION=true` are enabled, guarded read routes additionally require one trusted forwarded read-capable `X-Tenet-Authenticated-Roles` value from `viewer`, `operator`, or `admin`. Authenticated callers without one now fail with `403 Forbidden` plus `forbidden: authenticated viewer-capable role is required for this operator read route` before Tenet evaluates deployment visibility.
- For local filesystem desired-state repositories, Tenet now also looks for optional repository RBAC policy diagnostics at `rbac/policy.json`, `rbac/policy.yaml`, or `rbac/policy.yml`. Missing policy files do not block startup or change route enforcement. When present, `GET /v1/operator/context` evaluates the current trusted identity and `X-Tenet-Authenticated-Groups` group claims against that policy and returns a diagnostic-only `repositoryPolicy` object showing matched user/group grants, derived roles, deployment grants, project/environment scopes, and whether those derived grants would read or write. By default this remains diagnostic-only and route authorization still uses the trusted front-door role/deployment headers above. When filesystem catalog operators explicitly set `TENET_API_AUTHORIZE_WITH_REPOSITORY_RBAC_POLICY=true`, guarded read/write routes keep the same trusted identity requirement but use the evaluated repository-policy roles and deployment/project/environment grants instead of trusted role/deployment grant headers.
- `GET /v1/operator/context` is a read-only diagnostic endpoint for trusted front-door troubleshooting. It reports the normalized trusted identity, additive `identityHeaderSupport.canonical` / `identityHeaderSupport.aliases` lists for the accepted trusted identity header families, additive `identityProvenance` source metadata for the `id`, `name`, and `email` identity fields (`canonical`, `alias`, `managed_session_cookie`, or `absent`), additive persisted actor-attribution diagnostics (`actor`, `actorHeaderSupport`, `actorProvenance`, and `actorAttribution`) showing the effective plan/apply/audit actor, supported `X-Tenet-Actor-*` headers, compatible `X-User-*` actor aliases, and whether attribution came from explicit actor headers, trusted authenticated identity projection, or remained unavailable, plus the stable `actorAttribution.precedence` order (`explicit_actor_headers`, `actor_alias_headers`, `trusted_authenticated_identity`, `unavailable`) that explains how Tenet chooses persisted actor evidence, forwarded roles with read/write capability booleans, additive `roles.supportedNames` (currently `viewer`, `operator`, `admin`), additive `roles.supportedHeaderNames` (currently only `X-Tenet-Authenticated-Roles`, because role forwarding intentionally has no `X-User-*` compatibility alias), additive `roles.recognizedNames` / `roles.unrecognizedNames` diagnostics for forwarded values, and additive `roles.provenance.source` metadata (`canonical` for a normalized `X-Tenet-Authenticated-Roles` value, or `absent` when no trusted role value was forwarded), forwarded deployment allowlist, project/environment scopes, additive non-secret `desiredStateSource` diagnostics (filesystem versus GitHub catalog source, webhook match/ignored status vocabulary, and controller-refresh handoff availability such as Redis backend/channel without tokens or connection strings), and which auth/RBAC enforcement toggles are active for the request. Its additive `accessVerdicts.deploymentScopedRead.acceptsProjectEnvironmentScopes` and `accessVerdicts.deploymentScopedWrite.acceptsProjectEnvironmentScopes` fields explicitly tell UI clients when matching project/environment scopes can satisfy those route classes in addition to exact deployment grants. When deployment-read authorization is enforced and a catalog placement provider is available, `deploymentAccess.summary` also reports forwarded, matched/visible, and total unmatched deployment-name counts plus bounded unmatched-name evidence (`unmatchedNames`, with `unmatchedNamesTruncated` when the sample is incomplete), forwarded project/environment scope counts, bounded stale scope evidence (`unmatchedProjects` / `unmatchedEnvironments`, with matching truncation flags), and deterministic `projectEnvironmentExamples` (project, environment, region, AWS account, deployment count, and bounded example deployment names) so operators can spot stale front-door allowlists and project/environment coverage gaps. ### Smoke verification scope

Use `make smoke-local` for the fastest fixture-backed API/UI regression check when you only need direct-process validation without Docker or Redis.

It verifies:

## Using the UI

The intended operator flow is:

### Applications overview
Use the first page to scan:
- which applications exist
- account/environment
- sync and health state
- current runtime signal when it explains the row

The applications overview keeps only one primary row action visible: `_self` `Open application` to `/?page=application&deployment={deploymentName}`. Secondary handoffs move behind a `More actions` disclosure per row: `_self` `Open account`, deployment-scoped `_self` `Drift view`, `_self` `Plan/apply`, `_self` `Audit log`, and runtime-events links remain bookmarkable without crowding first-page triage. Application rows include a compact row-local `Last update` field using the joined `runtimeSummary.timestamp` or the existing `Latest runtime status` fallback, plus an optional `Runtime` line when the already-loaded runtime summary contains meaningful evidence, preferring controller change details, then runtime summary text, then concise condition or rollout-step cues; rows without real runtime evidence omit the `Runtime` line instead of rendering placeholder dashes. The landing page still includes an in-place `Refresh applications overview` control that re-runs only `GET /v1/overview/applications`, disables only while that overview fetch is active, keeps the current bookmarkable `q` / `sync` / `health` / `account` query state stable, and leaves the current application rows visible with explicit loading/error copy while the refresh runs or fails. The `health` query parameter accepts the same row labels operators see in the table (`Healthy`, `Progressing`, `Unhealthy`, or `Unknown`) so filtered links can be shared for health-focused triage. When filters are active, the summary card shows visible applications as `N of M`, echoes the active filter labels, and scopes `Last update` to the visible subset so operators do not mistake a narrowed result for the whole estate. Refresh-time `401` / `403` responses reuse the same trusted-front-door / access-denied guidance as the deeper bookmarkable drill-downs instead of falling back to generic refresh-error text. When an active `q` search matches hidden runtime-only evidence (for example controller change details, conditions, rollout step text, or artifact values), the matching row adds a concise `Search match` context line so the operator can see why it matched without turning the landing page into a dense runtime view.

The embedded shell also renders a compact `Operator context` banner above the toolbar. It calls `GET /v1/operator/context` and keeps the always-visible row to one status line: trusted front-door identity, trusted-header mode, read/write capability, and deployment-grant summary. Last-checked freshness and refresh/error details move into `Show access details` unless a refresh is actively failing, so the banner stays visible without pushing the applications list down the page. A small status-only live region announces checking/loading, ready identity, refresh, unavailable, and error states; the surrounding `Operator context` section is not a live region, so screen readers are not asked to announce the verbose diagnostics payload when the banner rerenders. Guarded deployment-scoped plan/apply writes require both `X-Tenet-Authorized-Projects` and `X-Tenet-Authorized-Environments` to match catalog placement when no exact deployment grant is forwarded. Verbose diagnostics now sit behind an explicit `Show access details` / `Hide access details` disclosure that stays in the operator's chosen expanded/collapsed state across `Refresh context` rerenders. The same expanded details now render non-secret `desiredStateSource` diagnostics so operators can see whether this instance is using filesystem or GitHub desired state, which GitHub repo/ref/path/base URL is configured when present, whether Redis controller-refresh handoff is available, and the webhook match/ignored reason vocabulary (`matched`, `repository_mismatch`, `ref_mismatch`, `path_untouched`, `deleted_ref_ignored`, and `controller_refresh_unavailable`) without exposing secrets or sending a test webhook. The authentication-boundary reminder distinguishes the default trusted-front-door path from an explicitly active Tenet-managed browser login: when `authRuntime.tenetManagedLogin.active=false`, guarded-read `401` recovery keeps the front-door retry copy; when it is active and reports a same-origin `loginRoute`, the recovery actions offer a `_self` `Sign in with Tenet-managed login` handoff that preserves the current bookmarkable path/query/hash as `returnUrl`. The same disclosure includes managed-login runtime diagnostics from `authRuntime.tenetManagedLogin` (configured/active/provider, required or missing settings, login/callback/session-cookie metadata, cookie attributes (`path`, `HttpOnly`, `SameSite`, configured secure override, current-request secure decision, and secure evidence such as HTTPS or forwarded-proto headers), and state/identity/session storage readiness), identity and role header provenance, supported identity header families from `identityHeaderSupport` (canonical `X-Tenet-Authenticated-Id`, `X-Tenet-Authenticated-Name`, `X-Tenet-Authenticated-Email`; compatibility aliases `X-User-ID`, `X-User-Name`, `X-User-Email`, with canonical values preferred when both are present), supported Tenet role labels from `roles.supportedNames`, the canonical supported role-header list from `roles.supportedHeaderNames` (`X-Tenet-Authenticated-Roles`, with no `X-User-*` role alias), the deployment access header list from `deploymentAccess.supportedHeaderNames` (`X-Tenet-Authorized-Deployments`, `X-Tenet-Authorized-Projects`, and `X-Tenet-Authorized-Environments`), bounded route examples, required trusted headers, project/environment visibility examples, stale-scope warnings, visible deployment examples, and access-verdict details remain available without pushing the main applications workflow down the page. Unsupported forwarded-role guidance uses the same capability split: forward `viewer`, `operator`, or `admin` for read capability, and forward only `operator` or `admin` for write capability. Operators can still immediately tell whether this API process is local-unrestricted, observed-only, read-only guarded, write-only guarded, or read/write guarded before interpreting guarded-route denials or likely-empty collection reads.

### Audit timeline
Use the audit page when you need immutable operator activity instead of controller-derived runtime history.

The page is backed directly by `GET /v1/audit-logs` and currently focuses on:
- newest-first `plan.created`, `apply.requested`, and `apply.transitioned` entries; transition rows expose previous/new status and step metadata so operators can see lifecycle progress without reopening the apply record
- a bookmarkable action filter that narrows the page and fetch route to exactly `plan.created`, `apply.requested`, or `apply.transitioned`
- a bookmarkable limit control in the audit toolbar that updates the fetch route and URL in place while preserving deployment and action filters; capped timeline responses also expose inline actions to expand to the next preset audit window or clear the limit cap without dropping deployment/action scope or applications-shell `q` / `sync` / `account` state
- an explicit in-place `Refresh audit log` control that re-fetches only `GET /v1/audit-logs`, disables only while that audit fetch is active, keeps the current bookmarkable `/?page=audit...` URL/query state stable, and shows a `Last refreshed` cue on the visible timeline so operators know when the current audit payload was fetched
- explicit in-page audit recovery controls: `Clear action/limit` appears on deployment-scoped audit pages when action or limit controls are active and resets only those controls while preserving the deployment context; `Clear audit controls` removes all active deployment/action/limit controls while preserving bookmarkable `q` / `sync` / `account` state and removing stale `#audit-*` section anchors
- clearable audit toolbar chips: active deployment, action, and limit controls each expose an accessible `Clear` button that removes only that one control, preserves the current shell pathname plus remaining `q` / `sync` / `account` / audit controls, removes stale `#audit-*` section anchors, and reloads the audit timeline through the existing page state
- active filter copy such as `Audit filters: action Apply requested (apply.requested) · Limit cap: latest 2` when you reopen `/?page=audit&action=apply.requested&limit=2`
- deployment-scoped filter copy such as `Audit filters: deployment payments-api-prod · action Apply requested (apply.requested) · Limit cap: latest 2` when you reopen `/?page=audit&deployment=payments-api-prod&action=apply.requested&limit=2`
- deployment / app / environment context
- the exact current audit read route, such as `GET /v1/audit-logs?deployment=payments-api-prod&action=apply.requested&limit=2`, rendered near the timeline intro so operators can confirm which scoped collection request backs the page before troubleshooting auth, empty states, or stale bookmarks
- per-row source metadata (`Source record · /v1/plans/{planId}` or `/v1/applies/{applyId}` plus `Source detail · ...` when the backend reports it) with `Open source record` / `Open source detail` raw JSON links so operators can inspect the immutable record and source snapshot without losing the current audit page context; each rendered row also exposes an `_self` `Share audit entry` link that preserves the current audit filters and jumps to that row's stable anchor for handoffs
- a compact visible-entry summary that counts total visible audit rows, `plan.created` rows, `apply.requested` rows, `apply.transitioned` rows, recorded actors, and unavailable/unknown actors for the current deployment/action/limit result set; when the API returns `resultScope`, the page also renders returned/matching entry counts, the applied router limit, deployment/action scope, and an explicit window status (`Capped response`, `Below cap`, or `Uncapped read`) so operators do not have to infer whether older matching audit rows may be hidden
- an `Audit timeline navigation` cue that summarizes the `Newest visible entry` and `Oldest visible entry`, plus `_self` `Jump to newest entry` and `Jump to oldest visible entry` links that preserve the current bookmarkable audit URL state while targeting the visible row anchors
- deployment-scoped chrome/body copy plus a deployment-specific empty state when `deployment={deploymentName}` is present and no persisted audit entries match
- deployment-scoped quick navigation that keeps `Applications overview`, `Back to application`, the current non-click `Audit log` destination, sibling `Drift view` / `Plan/apply` workspace links, and a hash-aware `Current section` / `On this page` pair for `Deployment context`, `Audit timeline`, and visible `audit-entry-*` row anchors such as `/?page=audit&deployment=payments-api-prod&limit=2#audit-entry-apply-...`
- the current audit section becomes a non-click chip when that hash is active, while the remaining audit sections stay as `_self` fragment links and otherwise fall back to `No section is currently targeted.`
- initial `GET /v1/audit-logs` auth failures now render operator-specific guidance instead of generic fetch-error copy: `401` tells the operator to reopen the same bookmarkable page through the trusted front door so authenticated identity can be provided, read-role `403` points admins at `Show access details` for role provenance, `roles.canRead`, and `X-Tenet-Authenticated-Roles`, and deployment-access `403` points at `deploymentAccess.summary`, access verdicts, unmatched grants, and the matching deployment, project, or environment scope
- keeps the current audit content visible with explicit loading/error copy while that in-place refresh is running or fails for the same bookmarkable route
- explicit actor-unavailable or actor-unknown labeling instead of fabricated identity
- `_self` links back into `/?page=application&deployment={deploymentName}` as `Open application drill-down`, into `/?page=drift&deployment={deploymentName}` as `Open drift view`, and into `/?page=plan&deployment={deploymentName}&planId={planId}&applyId={applyId}` as `Open plan/apply workspace` when those identifiers exist

### Account detail

Accounts with no deployment groups keep the account summary and quick navigation visible, then render an explicit empty state with `_self` `Applications overview` plus `Account JSON` / `Copy account read route` recovery handoffs so operators can open or copy the exact scoped read route instead of mistaking an intentionally empty account for a loading or rendering failure. The same account page now also renders compact `Quick navigation` chrome with an `_self` `Applications overview` return link plus a non-click `Account detail` chip so operators can stay oriented inside the bookmarkable account route without losing current `q`, `sync`, or `account` query state. That quick-nav now also adds a hash-aware non-click `Current section` chip plus an `On this page` group covering the `Account summary` and rendered project/environment groups, with a friendly fallback of `No section is currently targeted.` until the bookmarkable route includes a matching `#account-*` fragment such as `#account-summary`. Deployment rows with meaningful runtime/event evidence add a guarded `_self` `Open runtime events` link to `/?page=application&deployment={deploymentName}#application-runtime-events`, preserving the current `q`, `sync`, and `account` shell query state and omitting timestamp-only rows that do not offer useful runtime-event evidence. - workloads
- traffic routing

The backend now also exposes local-safe immutable apply-request routes:
- `POST /v1/applies/plans/{planId}`
- `GET /v1/applies?status=active`
- `GET /v1/applies?status=queued`
- `GET /v1/applies/{applyId}`
- `POST /v1/applies/{applyId}/claim`
- `POST /v1/applies/{applyId}/heartbeat`
- `POST /v1/applies/{applyId}/transitions`

These routes are additive and local-friendly. They persist immutable records to `TENET_APPLY_STORE_PATH`, keep live execution intentionally disabled by default in this slice, attach additive ordered `operations[]` rows so operators can inspect and share the future executor-facing `status` / `phase` / `target` / `summary` path without mutating AWS, and keep Tenet-authored stable operation `id` values aligned between reviewed plan previews, reloaded plan reads, created apply records, and reloaded apply reads. The direct `make smoke-local` path locks that those IDs are non-empty `op_...` values, remain unique within a preview, and are preserved when plan operations project into apply operations. The apply record also exposes an additive `lifecycle` block so later executor transitions can report timing and step progress on the same stable `applyId`. `POST /v1/applies/{applyId}/heartbeat` accepts `{"workerId":"worker-a"}`-style bodies for the currently claimed worker only, updates `claim.lastHeartbeatAt` and `claim.expiresAt`, preserves stable `applyId`, lifecycle state, operation state, details, and transition history, returns clear `400` malformed/invalid body (`invalid apply heartbeat request body`), `404` missing apply, and `409` wrong-worker/unclaimed/terminal-state responses, and performs no live AWS mutation. The embedded `/?page=plan` workspace now renders those lifecycle fields directly when present and leaves missing step/timing fields as placeholders instead of inventing synthetic progress. `POST /v1/applies/plans/{planId}` also re-validates the current deployment-detail fingerprint against the reviewed plan fingerprint before persisting; stale plans fail with `409 Conflict` and operator-facing refresh guidance instead of writing a new apply record. Set `TENET_AWS_ENABLE_APPLY=true` when you want the backend contract to create a queued immutable apply request on a fresh plan/apply pair and then hand that new `applyId` to the local-safe executor stub while keeping this slice mutation-free.

(`POST /v1/applies/{applyId}/transitions`) routes together. They persist and
advance Tenet apply metadata only; this local-safe record lifecycle does not
perform live AWS mutation. The read-only `/?page=applies` monitor is backed by

preserves the bookmarkable URL, translates claim heartbeat/lease metadata into

The same immutable stores also back a read-only audit projection route:
- `GET /v1/audit-logs`
- `GET /v1/audit-logs?deployment={deploymentName}`
- `GET /v1/audit-logs?action={action}`
- `GET /v1/audit-logs?limit={n}`
- `GET /v1/audit-logs?action={action}&limit={n}`
- `GET /v1/audit-logs?deployment={deploymentName}&limit={n}`
- `GET /v1/audit-logs?deployment={deploymentName}&action={action}&limit={n}`
- `GET /v1/controller/refresh/status`

This timeline is newest-first, projects persisted plan preview, apply request, and manual controller-refresh request records, includes a backend-authored stable `entryId` on each row for shareable UI anchors, derives `appRef` / `environmentRef` from the local catalog when possible, and keeps actor identity explicit: records created with additive `X-Tenet-Actor-Id`, `X-Tenet-Actor-Name`, and/or `X-Tenet-Actor-Email` headers, or the compatible `X-User-ID`, `X-User-Name`, and/or `X-User-Email` aliases, surface those fields, while unauthenticated or purely local requests still return `actor.available=false` plus `actor information is unavailable because no authenticated request context was available for this local request`. When both header families are present, the explicit `X-Tenet-Actor-*` values win. `deployment` is optional and must name exactly one deployment when present. `action` is optional and must be exactly `plan.created`, `apply.requested`, `apply.transitioned`, or `controller.refresh.requested` when present. A deployment filter with no matching persisted records still returns `200 OK` with `entries: []` so local operators can distinguish "no audit rows yet" from transport failure. `GET /v1/controller/refresh/status` is a read-only operator status shortcut over that same audit read model: it queries the latest `controller.refresh.requested` row with `limit=1`, returns `status`, `available`, `hasHistory`, `readOnly`, `latestReceipt`, and `resultScope`, reports `status=no_history` with `latestReceipt=null` when the audit store is configured but has no manual refresh receipts yet, and reports `503 Service Unavailable` with JSON `status=unavailable` when the audit read model is not configured or cannot be read. The embedded UI now renders the audit route at `/?page=audit` with explicit loading, empty, unavailable, and generic fetch-error states for non-auth failures, plus distinct operator guidance on initial `401` vs `403` reads and a safe action filter control that preserves bookmarkable `action` / `deployment` / `limit` URL state.

Tenet also exposes a read-only deployment events slice for the same drill-down workflow:
- `GET /v1/overview/deployments/{deploymentName}/events`
- `GET /v1/overview/deployments/{deploymentName}/events?limit={n}`
- `GET /v1/overview/deployments/{deploymentName}/events?limit={n}&source={source}` (including `source=unknown` for retained legacy events whose persisted source is blank or whitespace)

The embedded `/?page=application&deployment={deploymentName}` drill-down now renders a small `Controller runtime events` timeline from that route with explicit loading, empty, unavailable, and non-auth fetch-error states. Empty windows explicitly tell operators to increase `Event window` or refresh before treating controller history as absent; source-filtered empty windows name the selected source and tell operators to clear `Event source` or refresh before treating controller history as absent. The application page query window defaults to the latest 10 events and exposes bookmarkable `Event window` and `Event source` selectors that write `eventLimit` and optional `eventSource` into the application URL, plus a `Copy runtime events route` handoff for the same selected `GET /v1/overview/deployments/{deploymentName}/events?limit={n}[&source={source}]` read; refreshing happens in place and runtime events stay clearly separate from audit/auth history. Each rendered event row also exposes a `_self` `Share event` link that preserves the current application drill-down, `eventLimit`, and selected `eventSource` while targeting a stable row anchor, so incident handoffs can point at the exact controller event instead of only the whole timeline. This route returns controller-derived runtime events copied from persisted `status.history` plus an additive `sourceSummary` that normalizes blank persisted event sources into `unknown` for source-mix chips and exact `?source=unknown` filtering, plus an additive `managedDriftSummary` with explicit `total`, `high`, `medium`, and `low` counts across those returned history rows (zeroes are present when `events` is empty) and additive `retention` metadata for the retained controller-history slice. Successful responses also include additive `resultScope` metadata: default unbounded reads report `effectiveLimit: 0`, omit `requestedLimit`, set `returnedEventCount` / `totalEventCount` to the full returned event window, carry retained-history fields (`retentionLimit`, `retainedEventCount`, `retentionStatus`), and use `truncationStatus: "not_truncated"`; positive `?limit={n}` reads describe the selected newest-first window with deterministic query-limit truncation metadata because Tenet knows the persisted `totalEventCount` before slicing (`"truncated"` only when `totalEventCount > effectiveLimit`, otherwise `"not_truncated"`), while source-filtered reads additionally report `resultScope.sourceFilter`. `retentionStatus=at_retention_limit` is independent from that query-limit status and tells operators the effective retained controller-history cap is full. Malformed or non-positive limits fail with `400 Bad Request` and `invalid limit query`; invalid source filters fail before a controller-history read with `400 Bad Request` and `invalid source query`; `managedDriftSummary` then describes only the returned bounded rows. When a Redis controller-refresh handoff from an accepted GitHub desired-state push triggers reconciliation, the controller appends a non-secret `controllerRefresh` object to the persisted event with `requestId`, `deliveryId`, `repository`, `ref`, optional `after`, `requestedAt`, and `reconciledAt`; the application-page runtime-events timeline renders those fields as a concise `GitHub refresh evidence` cue with a shortened revision, delivery/request IDs, and request/receive/reconcile timestamps when present. Normal ticker reconciles omit that object and render as ordinary runtime events without placeholder GitHub labels, and deleted-ref webhook pushes still publish no refresh handoff and therefore create no runtime event. `make smoke-local` now locks the complementary default path by asserting fixture-empty events stay empty and ticker/default controller events do not include `controllerRefresh`. The application page renders those counts as `Managed drift summary · {total} total · {high} high · {medium} medium · {low} low` above the event list so operators can triage drift severity before opening individual event rows, and shows an in-shell `Open field-level drift` handoff to `/?page=drift&deployment={deploymentName}#drift-field-level` whenever those counts report managed drift so operators can jump directly into the field-level drift workspace. Example payload fragment: `{"deploymentName":"payments-api-prod","events":[{"summary":"Deployment has managed drift","managedDrift":[{"field":"runtimeContext.capacity.desired","severity":"high"}]}],"managedDriftSummary":{"total":1,"high":1,"medium":0,"low":0},"retention":{"limit":10,"retainedEventCount":1,"status":"within_retention_limit"},"resultScope":{"effectiveLimit":0,"returnedEventCount":1,"totalEventCount":1,"retentionLimit":10,"retainedEventCount":1,"retentionStatus":"within_retention_limit","limited":false,"truncationStatus":"not_truncated"}}`. It is intentionally operator-facing and refresh-based, not a full durable audit system yet, and the UI labels it separately from any future audit/auth history work. The same application page now also exposes a compact `Quick navigation` strip with a hash-aware `Current section` group plus an `On this page` group for only the currently rendered non-empty linked-resource sections and `Controller runtime events`, so operators can reopen anchors such as `/?page=application&deployment={deploymentName}#application-runtime-events` without changing the fetch contract or leaving the embedded shell. Empty zero-resource groups are suppressed on the page and in quick navigation; if an application truly has no linked resources yet, the page shows the explicit operator-facing empty state `No linked resources are currently reported for this application. Use controller runtime events below to inspect the latest rollout signals.` while still keeping the runtime-events section available. When one of those section hashes is active, Tenet renders it as a non-click current-section chip, removes it from the remaining `On this page` links, and otherwise shows the friendly empty state `No section is currently targeted.`. The section header includes the same `Event window`, `Event source`, and in-place `Refresh runtime events` controls, so the selected bounded/source-filtered window stays bookmarkable as `eventLimit` / `eventSource` while refresh re-fetches the matching events route and disables only while that events fetch is active. When that refresh returns `401` or `403`, the panel now shows the same trusted-front-door / access-denied guidance used on the other embedded read surfaces instead of generic fetch-error text. When the aligned runtime change label is `managedDrift`, the paired `changeDetails[]` text now stays single-slot but explains deterministic added, removed, and updated drift rows so operators can see what changed without diffing the whole `managedDrift[]` array by hand. When a deployment exists but no controller-authored runtime history has been persisted, the route still returns `200 OK` with `events: []` plus explicit zero counts in `managedDriftSummary`, `retention`, and `resultScope`, so the UI can keep the page stable and explicit during early runtime bootstrap.

The deployment-events `resultScope` also exposes compact aliases for clients that share operational data renderers: `returnedCount` mirrors `returnedEventCount`, and `truncated` mirrors `truncationStatus == "truncated"`.

When fixture-backed or early controller payloads have not yet persisted `rollout.execution[]`, Tenet keeps the read-only drill-down contract stable by synthesizing the same fallback rollout resources the operator would otherwise see from the controller-authored payload:
- `ecsRolling`: `ecsService` (`{deployment}-service`)

For the ECS rolling fallback service, the recent-log drill-down stays on the same operator workflow. Example route:
- `GET /v1/overview/deployments/worker-prod/resource-logs?resourceType=ecsService&resourceName=worker-prod-service`

When a service inspection identifies a concrete ECS task, operators and UI consumers can reuse the same route families with `resourceType=ecsTask`. The task resource name may be an ECS task ARN, `clusterArn` keeps the selected cluster from the parent ECS service handoff, and recent-log reads accept optional `containerName` to narrow the CloudWatch Logs lookup to a single container stream:
- `GET /v1/overview/deployments/worker-prod/resource-inspection?resourceType=ecsTask&resourceName=arn%3Aaws%3Aecs%3Aap-northeast-2%3A123456789012%3Atask%2Fworker%2Fabc123&clusterArn=arn%3Aaws%3Aecs%3Aap-northeast-2%3A123456789012%3Acluster%2Fworker-prod`
- `GET /v1/overview/deployments/worker-prod/resource-logs?resourceType=ecsTask&resourceName=arn%3Aaws%3Aecs%3Aap-northeast-2%3A123456789012%3Atask%2Fworker%2Fabc123&containerName=api&clusterArn=arn%3Aaws%3Aecs%3Aap-northeast-2%3A123456789012%3Acluster%2Fworker-prod&limit=5`

The embedded task resource page keeps that selected `clusterArn` bookmarkable through section links and lazy refreshes, shows it next to the selected container when present, lets operators use **Clear selected container** to remove only `containerName` while preserving task/cluster identity, and keeps **Clear selected cluster** available to remove only `clusterArn` while preserving the task ARN, `containerName`, limits, filters, and current hash.

The ECS task inspection payload keeps the same explicit envelope as other resource-inspection reads and adds an `ecsTask` object, for example:

```json
{
  "deploymentName": "worker-prod",
  "resourceType": "ecsTask",
  "resourceName": "arn:aws:ecs:ap-northeast-2:123456789012:task/worker/abc123",
  "available": true,
  "source": "ecs_service",
  "ecsTask": {
    "taskArn": "arn:aws:ecs:ap-northeast-2:123456789012:task/worker/abc123",
    "taskId": "abc123",
    "lastStatus": "STOPPED",
    "stoppedReason": "Essential container in task exited",
    "containers": [{"name": "api", "lastStatus": "STOPPED", "imageDigest": "sha256:abc123", "runtimeId": "runtime-api-123", "awslogs": {"group": "/ecs/worker", "stream": "ecs/api/abc123"}}]
  }
}
```

Operators can add an optional positive `limit` query parameter when they need a smaller, shareable recent-log envelope; Tenet threads that cap into providers that can limit natively (for example the built-in CloudWatch-backed ECS reads) and still applies router-level truncation to `entries[]` as a safety fallback while preserving the provider's newest-first order. Non-positive or non-numeric values return `400 Bad Request`. Successful responses include additive `resultScope` metadata with the optional `requestedLimit`, the `effectiveLimit`, `returnedCount` plus compatibility `returnedEntryCount`, optional `newestEntryTimestamp` / `oldestEntryTimestamp` values from the returned rows, conservative `truncationStatus` (`truncated`, `not_truncated`, `unknown`, or `not_applicable`), and boolean `truncated` so operators can tell which bounded read Tenet actually returned even when the provider could not cap natively. Tenet does not issue extra provider calls solely to prove exact totals or provider-wide time ranges beyond the bounded read. Local and compose smoke prove the provider-cap/router-fallback contract shape without requiring live CloudWatch rows. Example limited route:
- `GET /v1/overview/deployments/worker-prod/resource-logs?resourceType=ecsService&resourceName=worker-prod-service&limit=5`

Resource-log responses now include an additive `lookupContext` object so the payload stays self-describing during AWS troubleshooting:
- `lookupContext.region`
- `lookupContext.controlAccountId`
- `lookupContext.targetAccountId`
- `lookupContext.crossAccount`
- `lookupContext.observerRoleConfigured`

When a requested resource resolves through a backing resource, the same response can also include additive backing-resource identity:
- `backingResourceType`
- `backingResourceName`

`lookupContext` is present for both `available=true` and unavailable responses, so operators can still confirm the attempted lookup region/account path when `entries` is empty or `unavailableReason` is set. Successful empty responses also include additive `emptyReason` values (`no_recent_events` or `no_formatted_entries`) so API clients can distinguish a valid empty bounded read from an unavailable provider lookup without parsing `entries=[]` alone. For unavailable live AWS reads, capture the HTTP `Request-Id` response header next to the `lookupContext` object before escalating; the request ID anchors Tenet's structured API logs while the lookup context explains which region, control account, target account, and observer-role path the provider attempted. When a bootstrap-source request resolved through a backing Auto Scaling Group before the downstream lookup ran, `backingResourceType` and `backingResourceName` remain present on both success and explicit unavailable responses. Weighted-target-group traffic-routing resources such as `trafficShiftPlan`, `productionListenerRule`, `activeTargetGroup`, and `candidateTargetGroup` also preserve the same route and lookup-context envelope but now return `available=false` with `unavailableReason=no_log_source` because they do not have an independent log stream yet. See `docs/features/resource-recent-logs.md` for operator troubleshooting examples that distinguish bounded successful reads, AWS-unavailable supported-resource lookups, and route-stable no-log-source resources. The embedded UI renders the lookup-context fields directly as `Lookup region`, `Control account ID`, `Target account ID`, `Cross-account lookup`, and `Observer role configured` inside the `Recent logs` card, and when those additive backing-resource fields are present it also renders them there as `Backing resource type` and `Backing resource name`.
