# Tenet v1 Local Runtime

The local runtime packages the current read-only control-plane foundation as a Docker-friendly stack.

## What is implemented in this slice

- `tenet-api` serves the catalog and deployment-status read APIs.
- `tenet-controller` validates the repository catalog at startup, then reloads the repo and status snapshots on a timer to log abstract reconcile plans per deployment.
- a sample repository-shaped desired-state tree lives under `examples/local-repo/`, including YAML deployment manifests that can carry `binary` or `image` artifact intent.
- a sample filesystem-backed deployment-status file lives under `examples/local-status/deployments.json`, including the currently deployed binary/image metadata.
- `compose.yaml` wires both processes together so the repo can be explored locally without AWS credentials.

## Runtime contract

The local stack uses these inputs:

- `TENET_CATALOG_SOURCE=filesystem`
- `TENET_REPO_ROOT=/workspace/examples/local-repo`
- `TENET_STATUS_PATH=/workspace/examples/local-status/deployments.json`
- `TENET_PLAN_STORE_PATH=/tmp/tenet/plan-previews.json`
- `TENET_APPLY_STORE_PATH=/tmp/tenet/apply-requests.json`
- `TENET_CONTROLLER_REQUEUE_SECONDS=5` in the local Compose demo so controller planning logs refresh quickly
- `TENET_AWS_ENABLE_APPLY=false` by default in the local Compose demo; set it to `true` when you want queued-on-create immutable apply records plus a local-safe executor handoff on the same `applyId` without introducing AWS mutation

Both services mount `./examples` read-only. The `api` service also mounts a named volume on `/tmp`, which keeps `/tmp/tenet/plan-previews.json` and `/tmp/tenet/apply-requests.json` restart-safe so immutable plan/apply records survive the Compose `api` service restart used by `make smoke-docker`. That keeps the runtime deterministic and aligned with the current repo-backed architecture.

For `tenet-api`, the local runtime also enables request-scoped JSON logs for every API/UI request. Operators can rely on the stable fields `request_id`, `method`, `path`, `status`, `duration_ms`, and `result`, plus an `error` field on timeout/panic paths. `TENET_API_REQUEST_TIMEOUT` defaults to `30s`; set it to `0` to disable the timeout wrapper for local debugging.

## Trusted front-door auth

Front-door auth remains additive and opt-in. Tenet still supports the existing trusted-header mode for deployments that authenticate operators before requests reach the API. The local runtime can now also run an explicitly configured Tenet-managed GitHub OAuth, Google Workspace OIDC, or Okta OIDC browser login: `GET /auth/login/github`, `GET /auth/login/google`, or `GET /auth/login/okta` creates one-time callback state, redirects to the configured provider, the matching callback route exchanges the code, persists the normalized identity, and issues a signed `tenet_session` cookie (`HttpOnly`, `SameSite=Lax`) that later requests can project into the authenticated request actor. When that runtime is active, `GET /auth/logout` and `POST /auth/logout` clear only the Tenet-managed `tenet_session` cookie with matching attributes and redirect to a validated in-app `returnUrl` (default `/`); they do not sign the operator out of GitHub, clear an upstream front-door session, or change trusted front-door header precedence. The callback marks that cookie `Secure` whenever the request is already HTTPS, when a trusted front door forwards `X-Forwarded-Proto: https` / `Forwarded: proto=https`, or when operators explicitly enable the `TENET_AUTH_SESSION_COOKIE_SECURE` override; local HTTP development keeps the cookie non-`Secure` so `make smoke-local`-style workflows remain usable. `GET /v1/operator/context.authRuntime.tenetManagedLogin` also reports non-secret cookie-security evidence (`sessionCookieSecureOverride`, `sessionCookieSecureForRequest`, and `sessionCookieSecureSources`) so operators can distinguish an explicit secure-cookie override from HTTPS/front-door request evidence. The internal `authprovider` package contains GitHub OAuth, Google Workspace OIDC, and Okta OIDC authorization-code client primitives for managed-login integration, the internal `authidentity` package contains a small JSON-backed normalized identity-store contract, and the internal `authstate` package contains a JSON-backed OAuth callback state store with expiry and one-time consume semantics for future CSRF/state validation. When all runtime settings are present for GitHub OAuth, Google Workspace OIDC, or Okta OIDC, `tenet-api` loads the selected provider plus JSON-backed state/identity stores and reports `GET /v1/operator/context.authRuntime.tenetManagedLogin.active=true`. When any setting is absent the runtime stays disabled, reports non-secret `requiredSettings` / `missingSettings`, and never logs or returns configured secrets. The active managed-login runtime supports GitHub OAuth, Google Workspace OIDC, and Okta OIDC today; Okta SAML provider selection remains diagnostic-only, while provider-token refresh/revocation, upstream provider/front-door logout, and long-lived token lifecycle management remain future work. The legacy `/api/v1/auth/*` route family remains unregistered. That diagnostic also includes non-secret `requiredSettings` and `missingSettings` arrays so local operators can see exactly which inputs are absent or provider-incompatible without exposing configured secret values.

`GET /v1/operator/context.authRuntime.tenetManagedLogin` is also the lifecycle contract for this optional runtime: it reports `oauthStateTtlSeconds`, `sessionTtlSeconds`, `sessionExpiryEnforced`, stable cookie attributes (`sessionCookiePath=/`, `sessionCookieHttpOnly=true`, `sessionCookieSameSite=Lax`), explicit false `providerAccessTokenStored` / `providerAccessTokenReturned`, unsupported provider refresh/revocation flags, and logout boundaries (`logoutClearsSessionCookie` without provider-token revocation). Provider access tokens are used only for the callback profile lookup and are not persisted in identity/session stores or returned through diagnostics.

Reviewer verification for managed-login changes should include `go test ./internal/api ./cmd/tenet-api` for route/session/env wiring and `go test ./internal/authprovider ./internal/authidentity ./internal/authstate` for provider, normalized identity-store behavior, and one-time callback-state/CSRF helpers. Local and Docker smoke intentionally keep the default disabled runtime unless those OAuth environment variables are explicitly supplied. Treat managed-login release coverage as two complementary checks: smoke asserts the out-of-box `authRuntime.tenetManagedLogin.active=false` / trusted-front-door recovery path plus the non-secret lifecycle/token/logout boundary fields (`oauthStateTtlSeconds`, `sessionTtlSeconds`, `sessionCookiePath`, `sessionCookieHttpOnly`, `sessionCookieSameSite`, false provider-token persistence/refresh/revocation, and inactive Tenet-local logout), and focused router/session plus Node-backed embedded UI tests use local fake provider/context data to prove the configured active login, logout cookie clearing, expanded Operator context sign-out handoff, and sign-in handoff path without live GitHub, Google, or Okta credentials. The configured fake path also locks that the sign-out handoff uses `/auth/logout?returnUrl=...`, stays in the same shell, and tells operators it clears only the Tenet-managed session cookie.

Use these settings only when every request reaches Tenet through a front door that authenticates callers and strips any client-supplied `X-Tenet-Authenticated-*`, `X-Tenet-Authenticated-Roles`, `X-Tenet-Authorized-Deployments`, `X-Tenet-Authorized-Projects`, `X-Tenet-Authorized-Environments`, and trusted-alias `X-User-*` headers before forwarding trusted values. Do not expose a header-trusting `tenet-api` instance directly to untrusted clients.

Tenet currently has two intentionally separate identity header families:

| Header family | Trusted source | Current use |
| --- | --- | --- |
| `X-Tenet-Authenticated-*`, `X-Tenet-Authenticated-Roles`, `X-Tenet-Authorized-Deployments`, `X-Tenet-Authorized-Projects`, `X-Tenet-Authorized-Environments` | Authenticating front door only | Request-scoped route authorization, `GET /v1/operator/context` diagnostics, and optional projection into persisted plan/apply/audit actor fields when no explicit actor headers are present. |
| `X-Tenet-Actor-*` plus compatible `X-User-*` aliases | Local proxy, smoke, or trusted integration creating immutable records | Persisted actor metadata on plan previews, apply requests, and audit projections; this family does not authorize routes by itself. |

Keep that split intact when integrating an external front door: the provider should authenticate the user, strip spoofable inbound trust headers including `X-User-*` aliases, and then forward only the trusted authorization headers Tenet is configured to consume. Tenet-managed GitHub, Google OIDC, and Okta OIDC sessions are signed cookies minted only by their configured callback routes; `/auth/logout` only expires that Tenet-managed cookie and redirects back to a safe in-app URL. Tenet does not treat raw browser-supplied `X-User-*` headers as a login session, and clearing the Tenet cookie does not remove trusted front-door identity headers from a request.

The auth/RBAC toggles below are boolean examples. Set them to `true` only on API instances that are reachable exclusively through that trusted front door.

- `TENET_API_TRUST_AUTHENTICATED_HEADERS=true` trusts front-door-forwarded `X-Tenet-Authenticated-Id`, `X-Tenet-Authenticated-Name`, and `X-Tenet-Authenticated-Email`. When those explicit trusted fields are absent, the same trusted authenticated-identity path also accepts additive `X-User-ID`, `X-User-Name`, and/or `X-User-Email` aliases, and `X-Tenet-Authenticated-*` still wins over `X-User-*`.
- `TENET_API_ENFORCE_AUTHENTICATED_IDENTITY=true` requires authenticated identity on `POST /v1/plans/deployments/{deploymentName}`, `POST /v1/applies/plans/{planId}`, and `POST /v1/applies/{applyId}/transitions`. Unauthenticated requests fail with `401 Unauthorized` plus `unauthenticated: authenticated identity is required for this operator write route`. When explicit actor headers are absent, the trusted authenticated identity path projects that identity into persisted plan/apply/audit actor fields.
- `TENET_API_ENFORCE_OPERATOR_ROLE_AUTHORIZATION=true` trusts `X-Tenet-Authenticated-Roles`, normalizes comma-separated roles, and requires one operator-capable `operator` or `admin` role on those same operator write routes. Authenticated callers without one of those roles get `403 Forbidden` plus `forbidden: authenticated operator role is required for this operator write route` before any plan/apply lookup.
- `TENET_API_ENFORCE_DEPLOYMENT_READ_AUTHORIZATION=true` trusts `X-Tenet-Authorized-Deployments` as a comma-separated exact deployment allowlist for existing grants. It also accepts additive `X-Tenet-Authorized-Projects` plus `X-Tenet-Authorized-Environments` scopes for guarded deployment reads and immutable writes; Tenet only widens access when catalog placement proves the deployment belongs to both a forwarded project and environment. Exact deployment grants continue to gate those deployment-specific routes, including `POST /v1/plans/deployments/{deploymentName}`, `POST /v1/applies/plans/{planId}`, and the persisted `POST /v1/applies/{applyId}/transitions` write route. Guarded collections (`GET /v1/overview/applications`, raw catalog collections such as `GET /v1/catalog/deployments`, `GET /v1/status/deployments`, `GET /v1/overview/accounts`, and unscoped `GET /v1/audit-logs`) filter to the union of exact deployment grants and project/environment catalog matches. Missing, stale, or non-matching grants return `200 OK` with `[]` or `{"entries":[]}` on collection routes, while scoped reads return `401 Unauthorized` without trusted identity or `403 Forbidden` when no exact deployment or project/environment placement match proves access.
- deployment-scoped reads enforce trusted `X-Tenet-Authenticated-*` identity plus `X-Tenet-Authorized-Deployments` or matching project/environment scopes for exact grants, or matching `X-Tenet-Authorized-Projects` plus `X-Tenet-Authorized-Environments` catalog placement when read authorization is enabled.
- Local filesystem catalog sources may include an optional repository RBAC policy file at `rbac/policy.json`, `rbac/policy.yaml`, or `rbac/policy.yml`. Missing files are reported as `repositoryPolicy.configured=false` on `GET /v1/operator/context` and do not block startup. Present files are evaluated against trusted identity plus `X-Tenet-Authenticated-Groups` and projected into diagnostic-only `repositoryPolicy` fields (`matchedUsers`, `matchedGroups`, derived `roles`, `deploymentAccess`, and project/environment scopes). This does not replace trusted front-door route authorization yet; it is an operator-visible foundation for later policy-backed enforcement.
- `GET /v1/operator/context` is diagnostic-only and reports Tenet's normalized trusted identity, additive `identityHeaderSupport.canonical` / `identityHeaderSupport.aliases` lists for the accepted trusted identity header families, additive `identityProvenance` source metadata for the `id`, `name`, and `email` fields (`canonical`, `alias`, `managed_session_cookie`, or `absent`), additive persisted actor-attribution diagnostics (`actor`, `actorHeaderSupport`, `actorProvenance`, and `actorAttribution`) showing the effective plan/apply/audit actor, supported `X-Tenet-Actor-*` headers, compatible `X-User-*` actor aliases, and whether attribution came from explicit actor headers, trusted authenticated identity projection, or remained unavailable, plus the stable `actorAttribution.precedence` order (`explicit_actor_headers`, `actor_alias_headers`, `trusted_authenticated_identity`, `unavailable`), forwarded roles with `roles.supportedNames`, additive `roles.supportedHeaderNames` (currently only `X-Tenet-Authenticated-Roles` because there is intentionally no `X-User-*` role alias), `roles.provenance.source` metadata (`canonical` or `absent`) plus `roles.recognizedNames` / `roles.unrecognizedNames` diagnostics against that supported role set, forwarded deployment allowlist, project/environment scopes, and active auth/RBAC enforcement toggles for the current request. Its additive `enforcement` object summarizes the API process mode (for example `trusted_front_door_read_write`) plus whether trusted headers, guarded read/write routes, deployment-scoped allowlists, and collection filtering are active. Its additive `accessVerdicts` block summarizes whether common operator read, operator write, deployment-scoped read/write, filtered collection-read, and raw catalog-read route classes have the current request ingredients they need, including concrete `exampleRoutes` for each class, `acceptsProjectEnvironmentScopes` markers for deployment-scoped read/write classes that can be satisfied by matched project/environment placement, additive `requiredTrustedHeaders` (`X-Tenet-Authenticated-Id` or `X-User-ID`, `X-Tenet-Authenticated-Roles`, and the exact `X-Tenet-Authorized-Deployments` allowlist and/or matching `X-Tenet-Authorized-Projects` plus `X-Tenet-Authorized-Environments` scopes depending on the route class), plus reason strings for missing identity, missing roles, missing exact deployment allowlist membership, missing paired project/environment scopes, and collection reads that are likely empty because no visible deployments were forwarded or catalog placement data is unavailable to match project/environment scopes. The embedded `Operator context` banner now renders those verdicts beside the identity/role/allowlist summary and visually highlights blocked or likely-empty verdicts so operators do not have to mentally combine the raw fields before following drill-down links. When deployment-read authorization is enforced and catalog placements are available, `deploymentAccess.summary` additively reports how many forwarded deployment names or project/environment scopes matched catalog deployments, source-specific `exactDeploymentMatchedCount` and `projectEnvironmentMatchedCount` diagnostics for visible deployments, the total `unmatchedCount` before bounded sampling, deterministic `unmatchedNames` evidence for stale front-door configuration (with `unmatchedNamesTruncated` when more stale names exist than the sample includes), and bounded `projectEnvironmentExamples` showing visible project/environment/region/account groups with example deployment names. Use these diagnostics behind the same trusted front door to debug forwarded-header wiring and project/environment RBAC groundwork. If no forwarded names match catalog placements, the summary remains available with `emptyReason`; if placement data is unavailable, it reports `available=false` plus `unavailableReason`. The deployment access summary is diagnostic-only; it does not mint sessions, perform OAuth, authorize routes, or replace the guarded route checks. The enforcement summary and access verdicts are diagnostic-only too.
- The same trusted front-door read contract also covers `GET /v1/overview/accounts/{awsAccountId}`, raw desired-state catalog reads under `/v1/catalog/*`, `GET /v1/overview/accounts/{awsAccountId}/projects/{appRef}/environments/{environmentRef}`, `GET /v1/overview/applications/{deploymentName}`, `GET /v1/overview/deployments/{deploymentName}`, `GET /v1/overview/deployments/{deploymentName}/events`, `GET /v1/overview/deployments/{deploymentName}/resource-logs`, `GET /v1/overview/deployments/{deploymentName}/resource-inspection`, `GET /v1/status/deployments/{deploymentName}`, deployment-scoped `GET /v1/audit-logs`, and immutable stored reads `GET /v1/plans/{planId}` / `GET /v1/applies/{applyId}` using the persisted record deployment.

### Guarded-route troubleshooting workflow

Use `GET /v1/operator/context` as the first diagnostic before changing role or deployment headers. Treat the fields in this order:

1. Start in the embedded `Operator context` banner, or call `GET /v1/operator/context` directly when you are outside the UI.
2. `authRuntime.tenetManagedLogin` if you are configuring optional Tenet-managed GitHub OAuth, Google Workspace OIDC, or Okta OIDC session groundwork: it is read-only, reports missing settings/storage readiness, and only changes embedded `401` recovery into a `_self` managed sign-in handoff when `active=true` plus a same-origin `loginRoute` is present; otherwise default recovery stays on the trusted-front-door retry path. Then inspect `identity.authenticated`: `false` explains `401 Unauthorized` on guarded reads or writes; fix trusted identity forwarding first. `identityHeaderSupport` lists the exact canonical `X-Tenet-Authenticated-*` headers and compatibility `X-User-*` aliases accepted by this Tenet build, and `identityProvenance` shows whether each trusted identity field came from canonical headers, aliases, or was absent, so operators can spot front-door alias fallback without changing auth behavior. `actor`, `actorHeaderSupport`, `actorProvenance`, and `actorAttribution` separately show which persisted plan/apply/audit actor will be recorded from canonical `X-Tenet-Actor-*`, compatible `X-User-*`, trusted authenticated identity projection, or no available actor context; `actorAttribution.precedence` keeps the canonical actor header, actor alias header, trusted identity projection, and unavailable fallback order explicit for operators; this attribution diagnostic does not authorize routes. In the embedded UI, that same mode split keeps `401` recovery explicit: disabled/inactive managed-login deployments tell the operator to reopen the same bookmarkable URL through the trusted front door that forwards `X-Tenet-Authenticated-*` identity headers, while active Tenet-managed login deployments can offer `_self` `Sign in with Tenet-managed login` with the current URL preserved as `returnUrl`.
3. `roles.provenance.source`, `roles.supportedHeaderNames`, `roles.supportedNames`, `roles.recognizedNames` / `roles.unrecognizedNames`, and `roles.canRead` / `roles.canWrite`: `source=canonical` confirms Tenet received at least one normalized `X-Tenet-Authenticated-Roles` value, while `source=absent` tells operators to fix role forwarding before debugging deployment allowlists. `supportedNames` lists the exact Tenet role labels that can grant capability. Unsupported forwarded values appear under `unrecognizedNames`, so a header such as `auditor` is visibly different from a supported `viewer` / `operator` / `admin` role that grants capability. Role provenance intentionally has no `X-User-*` alias path, so missing roles must be corrected by forwarding `X-Tenet-Authenticated-Roles`. Missing read capability explains viewer-role `403` responses before any deployment allowlist check; missing write capability explains plan/apply `403` responses before plan/apply lookup.
4. `deploymentAccess.summary`: `matchedCount=0`, `emptyReason`, or non-empty `unmatchedNames` explains `200 OK` empty collections even when the request is authenticated and read-capable; `unmatchedCount` reports the full stale front-door-name count before the bounded sample is trimmed, and `unmatchedNamesTruncated=true` means the response shows only the first deterministic examples. When placement data is available, `exactDeploymentMatchedCount` and `projectEnvironmentMatchedCount` summarize how many visible deployments were proven by exact `X-Tenet-Authorized-Deployments` grants versus project/environment scope matches, while `visibleDeploymentExamples` names a bounded set of concrete visible deployments with app/environment/region/account context and `matchSources` values (`exactDeployment`, `projectEnvironment`, or both) so operators can see why each example is visible. For project/environment scopes, `forwardedProjectCount` / `forwardedEnvironmentCount` show how many normalized scopes arrived, while `unmatchedProjectCount` / `unmatchedProjects` and `unmatchedEnvironmentCount` / `unmatchedEnvironments` expose stale or non-matching scope values with truncation flags when samples are incomplete. `projectEnvironmentExamples` shows which visible project/environment groups the current front-door allowlist actually exposes, including the region, AWS account, deployment count, and bounded example deployments for each diagnostic group.
5. `accessVerdicts`: use the blocked or likely-empty verdict reason plus its bounded route examples, any additive `acceptedRoleNames` list (`viewer` / `operator` / `admin` for read route families and `operator` / `admin` for write route families), any collection-read `Collection scope: filtered to visible deployments` cue, any likely-empty `Collection result: likely empty` cue, any deployment-scoped `Scope grants: exact deployments or matching project/environment scopes` cue, and the embedded banner's full `Required trusted headers:` label, which is sourced from `requiredTrustedHeaders`, to identify the affected route family, then debug that class's exact identity, role, and/or `X-Tenet-Authorized-Deployments` front-door header wiring or matching `X-Tenet-Authorized-Projects` plus `X-Tenet-Authorized-Environments` scopes. Project/environment-scoped reads and deployment-scoped plan/apply writes require both forwarded scope headers and a catalog placement match; partial scopes, stale project/environment values, or unavailable catalog placement intentionally diagnose as likely `403`/empty instead of widening access. Exact `X-Tenet-Authorized-Deployments` membership remains accepted for those guarded deployment routes.

A safe local diagnostic mirrors the trusted headers your front door should forward:

```bash
curl -fsS http://localhost:8080/v1/operator/context \
  -H 'X-Tenet-Authenticated-Id: operator-123' \
  -H 'X-Tenet-Authenticated-Roles: viewer,operator' \
  -H 'X-Tenet-Authorized-Deployments: payments-api-prod,worker-prod' \
  -H 'X-Tenet-Authorized-Projects: payments-api' \
  -H 'X-Tenet-Authorized-Environments: prod-apne2'
```

The diagnostic response includes `actorHeaderSupport`, `actorProvenance`, `actorAttribution.precedence`, `roles.supportedNames`, `roles.supportedHeaderNames`, `roles.provenance.source`, `roles.recognizedNames`, `roles.unrecognizedNames`, and `accessVerdicts.*.acceptedRoleNames`; `supportedNames` lists the Tenet capability roles (`viewer`, `operator`, `admin`), `acceptedRoleNames` lists the exact role labels that satisfy each guarded route family (`viewer` / `operator` / `admin` for reads and `operator` / `admin` for writes), `supportedHeaderNames` lists the canonical trusted role header (`X-Tenet-Authenticated-Roles`) without any `X-User-*` role alias, `canonical` confirms a normalized `X-Tenet-Authenticated-Roles` value reached Tenet, while `absent` keeps missing role-header troubleshooting separate from missing identity or deployment-scope troubleshooting. Unsupported forwarded values such as `auditor` are explicit diagnostics without changing `roles.canRead` / `roles.canWrite` authorization semantics.

When forwarded project/environment scopes are stale, `deploymentAccess.summary.unmatchedProjects` and `deploymentAccess.summary.unmatchedEnvironments` remain troubleshooting evidence only. They explain likely empty collections or scoped deployment-route denials, but they do not mint a session or replace the guarded route checks.

### Manual `tenet-api` run without Docker

For manual `go run ./cmd/tenet-api` flows, `tenet-api` listens on `TENET_API_ADDR`, not `TENET_API_PORT`. Use `TENET_API_ADDR=:18083` as a safe local example before opening the UI so you do not collide with the default Docker stack on `localhost:8080`.

```bash
TENET_CATALOG_SOURCE=filesystem \
TENET_REPO_ROOT=$(pwd)/examples/local-repo \
TENET_STATUS_PATH=$(pwd)/examples/local-status/deployments.json \
TENET_API_ADDR=:18083 \
go run ./cmd/tenet-api
```

Then open:

```bash
http://localhost:18083/
```

### Docker stack smoke check

```bash
make smoke-docker
```

Use `make smoke-docker` when you need to validate the containerized local stack itself.

It verifies:

### Full Docker stack

```bash
make docker-up
curl http://localhost:8080/v1/catalog/summary
docker compose logs controller --tail=20
make docker-down
```

The `make docker-up` preflight intentionally fails fast when `localhost:8080` is already occupied by something other than this Compose stack. When that happens, inspect the listener with `lsof -nP -iTCP:8080 -sTCP:LISTEN`, clear a prior Tenet stack with `make docker-down` if needed, then rerun `docker compose up --build -d`.

Leave `TENET_AWS_ENABLE_APPLY` unset for the default disabled immutable apply contract. Set `TENET_AWS_ENABLE_APPLY=true make docker-up` when you want the same local stack to create queued immutable apply records on a fresh plan/apply pair and then let the local-safe executor advance that new `applyId`; that opt-in remains read-only and does not contact AWS.
