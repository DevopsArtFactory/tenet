# Tenet Overview UI

## Purpose

The Tenet UI is the operator-facing surface of the control plane.

It is intentionally designed to help someone answer a few practical questions quickly:
- What needs attention right now?
- Which application is affected?
- Which resource is involved?
- What operational context explains the current state?

Rather than starting from raw infrastructure objects, the UI starts from the application and lets the operator drill down only when they need more detail.

## Interaction model

### 1. Applications overview
This is the default landing page.

It is intentionally narrow and should stay easy to scan.

The first page focuses on:
- application name
- account/environment
- sync state
- health
- one primary drill-down action

The goal is fast triage, not completeness. The landing page keeps bookmarkable `q`, `sync`, `health`, and `account` filters; `health` uses the same row labels operators see in the table (`Healthy`, `Progressing`, `Unhealthy`, `Unknown`) so a health-focused view can be shared without losing the broader shell state. Malformed drill-down bookmarks that omit required context, such as an account page without `accountId` or an application/resource/workspace page without `deployment`, stop before any detail fetch and render a polite missing-context empty state with a `_self` `Back to applications` link that preserves those existing filters. When filters are active, the toolbar reset action becomes count-aware (`Clear N filters`) and its accessible label names the active filters so operators can tell how much bookmarkable state they are about to clear before pressing it. The first-load placeholder, filter-empty, no-application, and generic top-level empty/error states are polite atomic `role=status` regions so the operator-facing outcome is announced without making the whole shell live. The summary keeps deployment runtime freshness and UI read freshness separate: `Last update` / `Visible subset last update` still describe the newest runtime signal in the visible rows, while `Applications read refreshed` shows when the embedded page last fetched `GET /v1/overview/applications`; that read-freshness cue is a polite atomic `role=status` live region so assistive technology gets a narrow freshness announcement without changing visible copy or refresh behavior. Individual rows now include a compact row-local `Last update` field that reuses `runtimeSummary.timestamp` or the existing `Latest runtime status` fallback; project details remain omitted from the first page so operators use the application drill-down or account drill-down when they need that context. Browser tab titles are also route-aware safe text, so a shared or reopened `/?page=application`, `/?page=resource`, `/?page=drift`, `/?page=plan`, `/?page=audit`, or account drill-down URL identifies the active deployment/resource/account in browser chrome while preserving the static `Tenet Control Plane` HTML title as the non-JS fallback. The denser account/group deployment surface now lives on the secondary `/?page=account&accountId={awsAccountId}` drill-down, where the UI reuses `GET /v1/overview/accounts/{awsAccountId}` plus grouped project/environment sections instead of crowding the landing page; its toolbar exposes `Refresh account detail` next to the applications back link, its expandable deployment rows connect each keyboard-accessible row toggle to the controlled lazy-loaded detail panel with `aria-controls`, and its account summary includes an `Account detail read refreshed` cue after successful reads so operators can separate account-payload staleness from deployment runtime timestamps. The landing page also exposes a raw `Applications JSON` handoff to `GET /v1/overview/applications` for first-page troubleshooting, plus a small `_self` link to the dedicated bookmarkable audit route at `/?page=audit` (with optional `&deployment={deploymentName}`, `&action=plan.created|apply.requested`, and `&limit={n}` for a narrower newest-first window).

Initial auth failures on the landing read now follow the same shared operator-read contract as the other bookmarkable operator pages. `401 Unauthorized` on `/` normally tells the operator that Tenet is waiting for trusted front-door `X-Tenet-Authenticated-*` identity headers, and the rendered recovery actions include `_self` `Retry current page after front-door sign-in` so the current query/hash is preserved. If `GET /v1/operator/context` reports `authRuntime.tenetManagedLogin.active=true` with a same-origin login route, that same `401` recovery instead offers `_self` `Sign in with Tenet-managed login` and carries the current bookmarkable path/query/hash as `returnUrl`. Active enterprise SSO diagnostics use the same operator contract: `authRuntime.enterpriseSso.active=true`, empty `missingSettings`, and a same-origin `loginRoute` can offer a provider-specific `_self` handoff such as `Sign in with Okta SSO` through `/auth/login/okta`; the same label intentionally covers Okta SAML and Okta OIDC so operators see one clear Okta handoff when either runtime is active. Configured-but-inactive Okta diagnostics remain visible in Operator context and still render the trusted-front-door retry action instead of a clickable SSO handoff. Read-role `403 Forbidden` points at `#operator-context-access-details-panel` / `Show access details` for role provenance, `roles.canRead`, and forwarded `X-Tenet-Authenticated-Roles`, and deployment-access `403 Forbidden` points at `deploymentAccess.summary`, access verdicts, unmatched grants, and the matching deployment, project, or environment scope. Those `403` cards include `_self` `Open Operator context details` plus `_self` `Retry current page after access update`, deliberately avoiding the sign-in retry label for recognized-identity failures so operators focus on RBAC/deployment grants instead of re-authenticating blindly. Non-auth failures on initial embedded reads keep the same route-aware shape without auth-specific advice: the card names the active page, failed `GET ...` route, backend message, optional `Tenet request ID`, and `_self` `Retry current page` action so operators can escalate the exact failing read from a bookmarkable drill-down.

The `GET /v1/operator/context` endpoint behind the embedded banner also returns a diagnostic `enforcement` object and may return diagnostic `deploymentAccess.summary` JSON when Tenet can compare forwarded deployment allowlists or project/environment scopes with catalog placements. It also returns diagnostic `desiredStateSource` JSON for source/refresh troubleshooting. The expanded details render desired-state source mode (`filesystem` or `github`), non-secret GitHub repo/ref/path/base URL fields, Redis controller-refresh handoff readiness, and webhook match/ignored vocabulary so operators can troubleshoot source/refresh configuration without leaving the UI or exposing secrets. When that diagnostic reports an available GitHub/Redis handoff, the banner renders a safe DOM-built `Refresh controller` control that sends only `POST /v1/controller/refresh`; filesystem no-op and unavailable handoff diagnostics keep the control disabled, the current path/query/hash state is preserved, the button is disabled while the POST is in flight, and success, `filesystem_noop`, unavailable, `401`, `403`, and generic failures are announced through the same compact live-status path. The `401` / `403` branches reuse the shared operator-write auth guidance instead of generic fetch-error copy. The banner keeps the default view compact: identity plus one short status line for trusted-header mode, role capability, and deployment-grant summary stay always visible after the first successful context load so a local-unrestricted or observed-only API process is obvious without crowding the application list; last-checked freshness, refresh/error context, and verbose diagnostics live behind `Show access details` unless a refresh is actively failing. Only a small status-only live region announces checking/loading, ready identity, refresh, unavailable, and error states; the surrounding banner section is not `aria-live`, so expanding diagnostics or refreshing context does not ask assistive technology to announce the full access-verdict payload. Verbose diagnostics remain available behind an explicit `Show access details` / `Hide access details` disclosure that preserves the operator's expanded/collapsed choice across `Refresh context` rerenders, including enforcement summary text, an authentication-boundary reminder that keeps trusted front-door recovery as the default while noting active Tenet-managed browser login when the optional login/callback/session/logout routes report active, managed-login runtime diagnostics from `authRuntime.tenetManagedLogin` including session-cookie attributes and secure-cookie evidence (configured override versus HTTPS or forwarded-proto request evidence versus expected local HTTP), identity header provenance, role header provenance, supported Tenet role labels from `roles.supportedNames`, recognized capability roles, unsupported forwarded role labels that Tenet ignored for read/write capability checks, stale forwarded deployment names or stale project/environment scopes, project/environment evidence, project/environment visibility examples, visible deployment examples, and diagnostic `accessVerdicts` for common operator read/write, deployment-scoped, collection-read, and raw catalog-read route families with bounded route examples and required trusted headers. The expanded disclosure still shows deployment-scoped `acceptsProjectEnvironmentScopes` evidence in each verdict chip when the backend reports it; the summary is not an authorization source and the UI must not make client-side access decisions from it.

Initial auth failures on the secondary account drill-down now follow that same shared operator-read contract. `401 Unauthorized` on `/?page=account&accountId={awsAccountId}` tells the operator to reopen the same bookmarkable page through the trusted front door so authenticated identity can be provided, read-role `403 Forbidden` points at `#operator-context-access-details-panel` / `Show access details` for role provenance, `roles.canRead`, and forwarded `X-Tenet-Authenticated-Roles`, and deployment-access `403 Forbidden` points at `deploymentAccess.summary`, access verdicts, unmatched grants, and the matching deployment, project, or environment scope. Account and group JSON handoffs on that drill-down also expose `Copy account read route` / `Copy group read route` controls for the exact scoped `GET /v1/overview/accounts/...` paths so support handoffs do not require operators to reconstruct account/project/environment URLs by hand.

When the banner sees complete project/environment scopes but no exact deployment allowlist, it now shows a reminder instead of leaving the operator to infer authorization behavior from a later `403`: project/environment scopes can authorize guarded deployment reads and immutable writes when catalog placement matches both headers; `POST /v1/plans/deployments/{deploymentName}`, `POST /v1/applies/plans/{planId}`, and apply transitions still fail closed when the matching catalog placement is unavailable or stale.

### 1b. Audit timeline
The audit page is a sibling operator slice, not a replacement for the application drill-down.

It stays intentionally narrow:
- fetch `GET /v1/audit-logs`
- preserve optional bookmarkable `action`, `deployment`, and `limit` URL state on the audit route
- render a safe action filter control for exactly `plan.created`, `apply.requested`, and `apply.transitioned`
- render immutable plan/apply activity newest-first, including persisted apply lifecycle transitions as `apply.transitioned` rows with previous/new status and step metadata
- show each row's immutable `Source record` route plus `Source detail` route when present, with `Open source record` / `Open source detail` raw JSON links, so operators can jump from the audit evidence back to the stored plan/apply record or source snapshot they are troubleshooting
- give each audit row a stable `audit-entry-*` anchor plus an `_self` `Share audit entry` link that preserves deployment/action/limit filters, and surface those visible row anchors in deployment-scoped quick navigation so incident handoffs can jump to one immutable row instead of the whole filtered timeline
- make a selected deployment obvious in both the audit chrome and the audit body when `deployment={deploymentName}` is present, with deployment-context callout `_self` links to application detail and plan/apply so the next action is visible even before rows exist
- swap to filter-aware empty-state copy when selected deployment/action filters or a limit cap match no audit entries, while keeping the generic unfiltered empty state unchanged; deployment-scoped pages point operators at `Clear action/limit` to stay in context or `View global audit log` to remove the deployment scope, while unscoped action/limit states keep the `Clear audit filters` / `Clear audit controls` recovery path
- keep actor identity explicit as unavailable or unknown instead of inventing names
- expose an `Audit JSON` handoff from the audit timeline header that mirrors the current deployment/action/limit scope, so operators can open the raw `GET /v1/audit-logs...` response and inspect `resultScope` metadata without reconstructing query parameters manually
- show a `Last refreshed` cue beside the rendered timeline summary after successful audit reads so manual refreshes have an operator-visible freshness marker without changing the `/v1/audit-logs` payload contract
- provide `_self` links back into the existing `application` drill-down and `plan` workspace when deployment / plan / apply identifiers exist

This page is for immutable operator activity. It is separate from the controller-derived runtime events rendered on the application detail page.

### 2. Application detail
The second page focuses on one application and the resources that matter for understanding its rollout.

Resources are grouped into human-friendly sections such as:
- Workloads
- Traffic routing
- Config and access

The application quick-navigation section labels these resource groups with linked-resource counts, for example `Workloads (1)`, while the actual section headings stay as the plain group names.

Only non-empty linked-resource groups are rendered on the application page and in its quick-navigation section list. This keeps the drill-down focused on actionable operator surfaces instead of showing empty placeholders. If an application truly has no linked resources yet, the page should show the explicit empty state `No linked resources are currently reported for this application. Use controller runtime events below to inspect the latest rollout signals.` while still keeping the controller runtime events section available. That empty state includes an in-shell `_self` `Jump to runtime events` handoff to `#application-runtime-events` so operators can move directly to the remaining diagnostic surface.

The application-detail linked-resource filter is a client-side, bookmarkable `resourceFilter` query parameter. It matches normalized linked-resource `resource` type, `name`, and `description` text after the application-detail payload loads, so operators can narrow resource groups by type labels such as `ecsService`, concrete resource names, or descriptive rollout text. Filtering never changes the backing read route: application detail still reads `GET /v1/overview/applications/{deploymentName}`, and deeper resource/drift/plan links still preserve their existing route contracts. When `resourceFilter` hides rows in one or more reported resource groups, the UI keeps those sections visible with section-specific filtered-empty copy such as `No Traffic routing resources match resource filter "ecs". Clear the resource filter to show all Traffic routing resources.` so operators can distinguish filter impact from missing inventory. Active filters also switch section quick-nav labels to visible/total counts such as `Traffic routing (1 of 3)`. When the application read reports no linked resources at all, the page keeps the separate no-resource state `No linked resources are currently reported for this application. Use controller runtime events below to inspect the latest rollout signals.` Resource-filter updates and clear actions preserve the surrounding bookmarkable shell state (`q`, `sync`, `account`, `deployment`, and the current hash) while only changing or removing `resourceFilter`.

The page is backed by `GET /v1/overview/applications/{deploymentName}` and keeps the deeper `resource`, `drift`, and `plan` routes anchored to `GET /v1/overview/deployments/{deploymentName}`. Its summary chrome includes visible backing-read copy such as `Current application read: GET /v1/overview/applications/{deploymentName}` plus a client-side `Application detail read refreshed` live-status cue for that application-detail payload so operators can separate the page read time from runtime/status timestamps. The toolbar exposes an `Application JSON` handoff to that exact read model while preserving embedded `_self` drill-down links. A narrow controller-runtime-events slice is also rendered here by calling `GET /v1/overview/deployments/{deploymentName}/events` directly so the bookmarkable application detail stays operator-useful without pulling the full deployment-detail payload. That panel renders backend-authored `retention` / `resultScope` metadata beside the events list, including query-window status and controller-retention status, so empty retained history, query-limited responses, and retention-cap states are visibly distinct while the `eventLimit` URL parameter continues to drive refreshes and share links. Both detail surfaces preserve additive `sourceFingerprint` so the same reviewed payload can feed the immutable plan-preview flow without inventing a second client-side identity model. The companion `_self` `Audit log` link now opens `/?page=audit&deployment={deploymentName}` so the operator keeps the same deployment context when switching into the immutable audit slice.

Resource rows keep `_self` evidence handoffs scoped to the same embedded route. `Open live inspection` targets `#resource-live-inspection`; `Open recent logs` targets `#resource-recent-logs` for route-stable recent-log resources, including CodeDeploy application/deployment-group/listener/task-set resources plus weighted `trafficShiftPlan`, `productionListenerRule`, `activeTargetGroup`, and `candidateTargetGroup` rows. The shortcut is still honest when the final resource page returns explicit `no_log_source` copy because that is useful operator evidence, not a broken route.

Initial auth failures on that application-detail read are now intentionally operator-specific: `401 Unauthorized` tells the operator to reopen the same bookmarkable page through the trusted front door so authenticated identity can be provided, read-role `403 Forbidden` points at `#operator-context-access-details-panel` / `Show access details` for role provenance, `roles.canRead`, and forwarded `X-Tenet-Authenticated-Roles`, and deployment-access `403 Forbidden` points at `deploymentAccess.summary`, access verdicts, unmatched grants, and the matching deployment, project, or environment scope. When `TENET_API_ENFORCE_DEPLOYMENT_READ_AUTHORIZATION=true` is enabled, the backend now enforces that narrow read gate using trusted `X-Tenet-Authenticated-*` identity plus either trusted `X-Tenet-Authorized-Deployments` membership or matching `X-Tenet-Authorized-Projects` plus `X-Tenet-Authorized-Environments` catalog placement. When `TENET_API_ENFORCE_OPERATOR_ROLE_AUTHORIZATION` is also enabled, the same guarded read path additionally requires one trusted forwarded read-capable `X-Tenet-Authenticated-Roles` value from `viewer`, `operator`, or `admin`, returning `403 Forbidden` plus `forbidden: authenticated viewer-capable role is required for this operator read route` before deployment filtering. Other statuses keep the existing unavailable/generic fetch-error behavior.

This page should help the operator decide which concrete resource to inspect next while still exposing the most recent controller-derived runtime timeline in a clearly non-audit section.

### 3. Resource detail
The final page is where deeper operational context belongs.

This page is where Tenet can still show the deeper operational slices:
- rollout state
- runtime history
- conditions
- live inspection
- artifact context
- recent logs plus the explicit lookup path Tenet used

The goal is to make troubleshooting possible without forcing the user to jump directly into raw AWS consoles for the first step.

The embedded resource page now includes a top-level `Resource JSON` handoff plus a `Refresh resource detail` action for the same `GET /v1/overview/deployments/{deploymentName}` payload. Refresh runs in place, preserves the canonical bookmarkable `/?page=resource&deployment={name}&resourceType={type}&resourceId={id}` URL, accepts older `resourceName={name}` bookmarks as a compatibility fallback when `resourceId` is absent, re-resolves the selected resource from the refreshed payload, and keeps the last successful resource detail visible while refresh-time loading/error guidance renders above it. ECS service live-inspection payloads can expose `Recent ECS tasks` rows with task/container/AWS logs context and `_self` handoffs into task-specific live-inspection or recent-log anchors; direct `ecsTask` resource pages render the task evidence payload without requiring operators to open raw JSON. Auto Scaling Group live-inspection payloads for `candidateAutoScalingGroup` and `serviceAutoScalingGroup` also render an `_self` `Open EC2 console logs` handoff to the same bookmarkable resource page's `#resource-recent-logs` panel, while unsupported generic `autoScalingGroup` resources intentionally do not get that link. The same page also includes a dedicated `Live inspection` panel that lazy-loads `GET /v1/overview/deployments/{deploymentName}/resource-inspection?resourceType={type}&resourceName={name}` for the selected resource while keeping the bookmarkable `/?page=resource...` route unchanged. That panel should always render an explicit state:
- loading
- unavailable, with lookup context plus friendly copy mapped from `unavailableReason`; unknown reason codes use a generic operator-facing fallback instead of raw machine codes
- empty, when the route is available but there is no typed payload to show yet
- supported, with operator-friendly fields for `ecsService`, Auto Scaling Group, `userDataBootstrapSource`, and traffic-routing summary payloads, including ECS deployment-configuration evidence and the launch-template bootstrap-source comparison Tenet already uses for managed drift
- a `Refresh live inspection` action that re-runs only the inspection route in place, disables while that inspection fetch is active, and preserves the bookmarkable resource URL

The resource-detail Troubleshooting summary is a derived UI contract, not a separate API read. It is derived from the selected resource identity plus the latest completed Live inspection state and the latest completed Recent logs panel state, and it covers loading, empty, unavailable, and fetch-error states without hiding the selected resource. It now also includes any selected lookup scope (`containerName`, `clusterArn`, or `instanceId`) and a compact Evidence freshness row that timestamps completed panel reads without inventing times for panels not refreshed yet, so those states do not hide the scoped selector or force operators to scroll into both lazy panels before judging staleness. The summary can point operators at the most useful next panel, but the page still keeps `Current resource read: GET /v1/overview/deployments/{deploymentName}` visible before lazy Recent logs or Live inspection reads resolve, so the selected resource's backing deployment-detail read remains clear while lazy panel evidence changes.

The application/resource/drift/plan/audit drill-down pages now also render explicit breadcrumb chrome before their deeper sections. Those breadcrumbs keep prior drill-down levels as `_self` links, keep the current destination as a non-click chip, include the account step when the loaded deployment detail already exposes `awsAccountId`, and omit links that Tenet cannot build from already-loaded data. Resource, drift, plan, and deployment-scoped audit pages still keep their compact quick-navigation strip above the deeper detail sections. Resource pages also keep direct `_self` `Applications overview`, `Back to application`, `Jump to live inspection`, and `Jump to recent logs` handoffs so operators can move from selected identity to the top-level app list, parent application, or focused evidence without scanning the entire page. That navigation is intentionally data-local: it builds `_self` links for `Applications overview`, `Back to application`, `Drift view`, `Plan/apply`, `Audit log`, selected-resource evidence panels, and sibling linked resources using only the already loaded deployment-detail payload plus preserved URL state. It should not introduce nested interactive controls or a second fetch path just to support lateral navigation.

For recent logs, the embedded card keeps backend lookup context visible with operator-facing labels such as `Lookup region`, `Control account ID`, `Target account ID`, `Cross-account lookup`, and `Observer role configured`. Those fields stay visible in unavailable and empty states so operators can see where Tenet looked before switching to raw AWS troubleshooting. That card also exposes `Refresh recent logs` with the same in-place URL-preserving behavior and per-panel loading disablement, and completed panel payloads render a client-side `Last refreshed` cue beside request metadata so operators can judge staleness even when the provider returns `available=false`; denied reads still stay focused on trusted-front-door/request-correlation guidance.

The deployment-events route is intentionally read-only and controller-derived. It reflects persisted runtime history entries, returns `events: []` when a deployment exists without history yet, and should not be treated as a full durable audit system. Each returned row includes an additive backend-authored `eventId` derived from stable persisted event metadata so shared runtime-event anchors do not depend on mutable summary/detail wording. Operators and UI clients can add `?source={source}` to keep only exact source matches before any bounded window is applied, and can add `?limit={n}` with a positive integer to bound the newest-first rows; the embedded application page defaults to `?limit=10` and exposes bookmarkable `Event window` and `Event source` selectors that store selected values as `eventLimit` and optional `eventSource` on `/?page=application&deployment=...`, so operators can widen/narrow controller history or isolate one source without leaving or losing the drill-down URL. Successful event-window reads also render a client-side `Last refreshed` cue next to the window metadata, while unavailable/denied reads omit that freshness marker so operators do not treat recovery copy as current evidence. Each rendered event row includes a `_self` `Share event` link that targets a stable row anchor while preserving the current application URL, `eventLimit`, and selected `eventSource`, so incident handoffs can identify one controller event without asking the recipient to scan the full timeline; invalid or non-positive limit values return `400 Bad Request` with `invalid limit query`, invalid source filters return `400 Bad Request` with `invalid source query`, and successful responses include additive `resultScope` metadata for both default unbounded reads and bounded/source-filtered event-window reads, including optional `newestEventTimestamp` / `oldestEventTimestamp` values derived from the returned rows when those rows carry timestamps, and the `managedDriftSummary` counts only returned rows. When a bounded read returns no rows, the embedded empty state tells operators to widen `Event window` or refresh before treating controller history as absent; when an `Event source` filter returns no rows, the empty state names the source filter and tells operators to clear it or refresh before treating controller history as absent. GitHub desired-state pushes that publish Redis controller-refresh handoffs add optional `events[].controllerRefresh` evidence (`requestId`, `deliveryId`, `repository`, `ref`, optional `after`, `requestedAt`, `receivedAt`, and `reconciledAt`) to the controller-authored event; the application detail renderer shows those fields as a concise `GitHub refresh evidence` cue with shortened revision, delivery/request IDs, and request/receive/reconcile timestamps when present. Normal ticker reconciles and deleted-ref webhook no-ops omit that object, and the UI leaves those ordinary runtime rows free of placeholder GitHub labels. The application drill-down renders the route's additive `managedDriftSummary` as `Managed drift summary · {total} total · {high} high · {medium} medium · {low} low` above the event list so operators can spot severity distribution before scanning individual rows, then shows an in-shell `Open field-level drift` handoff to `/?page=drift&deployment={deploymentName}#drift-field-level` when those counts report managed drift. The application drill-down exposes the same `Event window`, `Event source`, and `Refresh runtime events` actions on that panel so operators can re-run only the selected `GET /v1/overview/deployments/{deploymentName}/events?limit={n}[&source={source}]` window in place, preserve the bookmarkable `/?page=application...&eventLimit={n}[&eventSource={source}]` URL, and disable just that panel action while the events fetch is in flight. Auth-gated `401` / `403` responses on that in-place refresh now reuse the same trusted-front-door / access-denied guidance as the other embedded read surfaces instead of generic fetch-error copy. When an event's aligned change label is `managedDrift`, the paired `changeDetails[]` text now stays single-slot but explains deterministic added, removed, and updated drift rows so the timeline remains readable without diffing raw `managedDrift[]` arrays.

The drift workspace stays read-only and now exposes `Refresh drift workspace` on the field-level drift section so operators can re-run only `GET /v1/overview/deployments/{deploymentName}` in place, keep the bookmarkable `/?page=drift...` route unchanged, see `Current workspace read: GET /v1/overview/deployments/{deploymentName}.` plus an explicit `Drift viewer read refreshed` cue in the workspace header, and see explicit loading/error copy without clearing the current drift workspace content while the refresh is in flight. Its top-level toolbar includes `Workspace JSON` for the same deployment-detail read model. Its compact drift summary labels high/medium/low severity counters as visible-row counts so query or severity filters do not make filtered counts look like the total baseline. Field-level rows also expose `_self` `Share drift row` links that append stable row-level `#drift-row-...` anchors to the same drift workspace URL, preferring backend row identifiers when present and falling back deterministically for legacy derived rows. That same drift shell now surfaces direct `_self` resource drill-down links in its quick-navigation strip using the already-loaded grouped normalized resource inventory from the deployment detail payload, and it renders explicit `No linked resources are available in this workspace yet.` copy instead of broken links when the inventory is empty. The breadcrumb and quick-navigation layers deliberately complement each other here: breadcrumbs preserve the drill-down path, while quick-nav keeps lateral workspace/resource jumps available. The backing deployment-detail contract now also treats controller-owned completed sync defaults as `Drifted` when the same payload carries concrete controller-authored `managedDrift[]` rows, while preserving seeded sync evidence and active rollout states. For EC2 deployments using `asgWeightedTargetGroups` or `asgInstanceRefresh`, those controller-authored rows can include live-backed Auto Scaling Group capacity evidence under `runtimeContext.capacity.desired`, `runtimeContext.capacity.min`, and `runtimeContext.capacity.max` when read-only AWS inspection succeeds. ECS `ecsCodeDeploy` and `ecsRolling` deployments can now also publish live ECS-backed rows under `runtimeContext.capacity.desired` and `runtimeContext.taskDefinition.image` from read-only ECS service inspection when the service desired count and a single task-definition container image can be resolved. Fixture-backed, older, or no-AWS cases keep the existing fallback path without synthetic live rows.

Loaded runtime-event timelines also render a compact `Runtime event navigation` strip above the rows. It summarizes the `Newest visible event` and `Oldest visible event`, exposes `_self` `Jump to newest event` and `Jump to oldest visible event` handoffs, and preserves the current `eventLimit` / `eventSource` URL state so shared event anchors continue to reopen the same bounded source-filtered window.

Deployment-events `resultScope` includes compact `returnedCount` and `truncated` aliases beside `returnedEventCount` and `truncationStatus`, plus `sourceFilter` when an exact `?source=` filter was applied, so UI/client code can share bounded-result rendering with other operational data surfaces without dropping the event-specific fields. Exact-cap bounded reads report `truncationStatus: "unknown"` and keep `truncated: false`, matching recent-log bounded-read semantics when Tenet cannot prove whether older rows exist.

That same `GET /v1/overview/deployments/{deploymentName}` entry contract now distinguishes auth failures for the bookmarkable `/?page=resource...` and `/?page=drift...` routes: `401 Unauthorized` tells the operator to reopen the same bookmarkable page through the trusted front door so authenticated identity can be provided, read-role `403 Forbidden` points at `#operator-context-access-details-panel` / `Show access details` for role provenance, `roles.canRead`, and forwarded `X-Tenet-Authenticated-Roles`, and deployment-access `403 Forbidden` points at `deploymentAccess.summary`, access verdicts, unmatched grants, and the matching deployment, project, or environment scope. The same narrow read gate also covers `GET /v1/overview/applications`, which now requires trusted identity and filters returned rows through the union of trusted `X-Tenet-Authorized-Deployments` exact grants and matching `X-Tenet-Authorized-Projects` plus `X-Tenet-Authorized-Environments` catalog placement, returning `200 OK` with `[]` when no grant matches anything. When `TENET_API_ENFORCE_OPERATOR_ROLE_AUTHORIZATION` is also enabled, those same guarded read routes additionally require one trusted forwarded read-capable `X-Tenet-Authenticated-Roles` value from `viewer`, `operator`, or `admin` before Tenet evaluates the deployment allowlist or collection filtering. `GET /v1/overview/accounts` follows the same collection contract and filters returned account aggregates through the trusted allowlist. Unscoped `GET /v1/audit-logs` now follows that same collection contract under read enforcement: it requires trusted identity, filters returned audit entries through the trusted `X-Tenet-Authorized-Deployments` allowlist, and returns `200 OK` with `{"entries":[]}` when the allowlist is omitted or no audit rows remain visible. Scoped account JSON routes now follow the same front-door contract: `GET /v1/overview/accounts/{awsAccountId}` and `GET /v1/overview/accounts/{awsAccountId}/projects/{appRef}/environments/{environmentRef}` require trusted identity, filter their deployment lists to authorized deployments only, recompute additive counters from that visible subset, and return the existing `403 Forbidden` deployment-read denial when the authenticated operator has no authorized deployments left in that scope. ## Design principles

The UI should continue to follow these principles.

### Progressive disclosure
Do not put everything on the first page.
Start with application status, then reveal deeper information through drill-down.

### Operator-first clarity
Prefer names, groups, and labels that are understandable during a rollout or incident.
The UI should reduce cognitive load, not increase it.

### Explicit states
Loading, empty, unavailable, and error states should all be visible and understandable.
A blank area is not acceptable UX.

### Stable navigation
Pages and links should preserve context so operators can bookmark, share, and return to the exact view they need.

### Lightweight delivery
The UI remains embedded and framework-light for now. That keeps the product easy to run and iterate on while the control-plane model is still settling.

## Backing model

Conceptually, the UI is powered by joined read models built from:
- desired deployment state from the repository
- runtime status from Tenet's status layer
- resource and rollout context derived for operators

That means the UI is not just a thin log viewer or a direct mirror of raw provider APIs. It is intended to be a control-plane view designed around operational understanding.

Today the UI already supports:
- applications overview
- account drill-down for grouped project/environment context
- application detail drill-down
- resource detail drill-down
- read-only drift workspace plus the mutation-safe plan/apply workspace with bookmarkable URLs
- deployment events derived from persisted runtime history
- recent operational context for supported resources

Future iterations should continue improving:
- clarity of drill-down paths
- operator-focused wording
- troubleshooting usefulness
- quality of empty/unavailable/error states
- overall usability under real deployment pressure
